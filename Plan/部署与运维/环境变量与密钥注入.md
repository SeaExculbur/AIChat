# 环境变量与密钥注入——从 `.env` 到容器进程

> 时间：2026-10-22
> 解决一个常见困惑：源码里写的是 `os.getenv(...)`，服务器上从没手敲过 `export`，密钥到底是怎么进去的？

---

## 一、先分清四个东西

| 名称 | 管什么 | 和谁有关 |
|---|---|---|
| `.gitignore` | 哪些文件不进 Git 仓库 | Git |
| `.dockerignore` | 哪些文件不进 Docker 构建上下文 | `docker build` |
| `env_file` | 容器启动时从哪个文件读环境变量 | `docker compose up` |
| `os.environ` | 当前进程实际拥有的环境变量 | Python 运行时 |

它们互相独立。一个文件可以"不进 Git、不进镜像"，但仍然"在宿主机上，被 Compose 读进容器环境"。

---

## 二、本地开发：`load_dotenv()` 读 `.env`

`backend/config.py`：

```python
from dotenv import load_dotenv
load_dotenv()
```

`load_dotenv()` 会在当前目录及上层查找 `.env`，把里面的键值对写进 `os.environ`。

本地目录：

```
backend/
├── .env            ← 开发用，含本地 DeepSeek Key / SQLite 地址
└── config.py
```

运行 `python app.py` 时，工作目录是 `backend/`，所以加载的是 `backend/.env`。

之后：

```python
os.getenv("DEEPSEEK_API_KEY")
os.getenv("DATABASE_URL")
```

读的就是刚被填进去的值。

### 优先级

`load_dotenv()` 默认 `override=False`：**已经存在的环境变量不会被 `.env` 覆盖**。

所以如果你在 shell 里先 `export DEEPSEEK_API_KEY=...`，再运行程序，shell 的值会赢。

## 三、生产：Compose 的 `env_file` 注入

`docker-compose.yml`：

```yaml
flask:
  env_file:
    - ./backend/.env.production
```

流程：

```
宿主机 /root/AIChat/backend/.env.production
        │ docker compose up 时读取
        ▼
要创建的容器的 Env 配置
        │ Docker Engine 创建容器
        ▼
容器 PID 1 的环境变量
        │ gunicorn fork worker
        ▼
每个 worker 继承同一份环境变量
        │ os.getenv()
        ▼
app.py / config.py / chat.py
```

**关键**：

- 应用**不读** `.env.production` 文件本身
- 读文件的是 Docker Compose
- 文件一直在宿主机上，容器里没有它
- 容器里只有"变量名=值"

---

## 四、根目录 `.env` 是另一条线

项目根目录还有一个 `.env`：

```bash
/root/AIChat/.env
```

内容只有一行：

```
POSTGRES_PASSWORD=...
```

它用于 **Compose 的变量插值**：

```yaml
db:
  environment:
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

Compose 会自动读取项目根目录的 `.env`，把 `${POSTGRES_PASSWORD}` 替换成真实值。

它**不参与应用运行时**，只影响 Compose 怎么生成 db 容器的配置。

### 两个文件的分工

| 文件 | 谁读 | 用途 |
|---|---|---|
| `backend/.env.production` | Compose 的 `env_file` | 注入 flask 容器的 `DEEPSEEK_API_KEY`、`JWT_SECRET_KEY`、`DATABASE_URL` 等 |
| 根目录 `.env` | Compose 的变量插值 | 提供 `${POSTGRES_PASSWORD}`，生成 db 容器环境 |

`backend/.env.production` 里的 `DATABASE_URL` 和根 `.env` 里的 `POSTGRES_PASSWORD` 必须是同一个密码，否则 flask 连不上 db。

## 五、三层"是否包含"

| 位置 | `.env.production` | 根 `.env` | 说明 |
|---|---|---|---|
| Git 仓库 | ❌ | ❌ | `.gitignore` 排除 |
| Docker 镜像 | ❌ | ❌ | `backend/.dockerignore` 的 `.env*` 排除；根 `.env` 不在构建上下文 |
| 宿主机 | ✅ | ✅ | 部署时上传，权限 600 |
| 容器文件系统 | ❌ | ❌ | 只有环境变量，没有文件 |
| 容器进程环境 | ✅ | ❌ | flask 拿到 `.env.production` 的值；db 拿到 `POSTGRES_PASSWORD` |

**镜像里没有密钥**，所以把镜像推到仓库也不会泄露。密钥是"运行时输入"，不是"构建产物"。

---

## 六、上传和 Docker 是两件独立的事

源码上传用的是：

```bash
tar -czf - ... backend frontend nginx docker-compose.yml | ssh aichat 'tar -xzf - -C /root/AIChat'
```

- `backend/.env.production` 藏在 `backend/` 里，没有被 `--exclude` 排除 → 跟着 tar 到了服务器
- 根目录 `.env` 是后来单独用 `scp` 传的
- Docker 全程没有参与这次文件传输

**开发用的 `backend/.env` 也会被 tar 带上去**（tar 的排除列表里没有它）。生产不需要它，建议删掉：

```bash
rm /root/AIChat/backend/.env
```

删之前确认路径，不要误删 `.env.production`。

---

## 七、容器环境变量在"创建时"固定

环境变量是容器配置的一部分，容器创建后就固定了。

```bash
docker compose restart flask          # ❌ 还是旧的环境变量
docker compose up -d --no-deps --force-recreate flask   # ✅ 重新创建，读新文件
```

`restart` 只是停止再启动同一个容器，不会重新读取 `env_file`。

## 八、数据库密码的特殊性

`POSTGRES_PASSWORD` 只在**数据库首次初始化**（数据目录为空）时用来创建用户。

已有数据卷时，改这个环境变量**不会**改数据库里的密码。需要：

```sql
ALTER USER aichat WITH PASSWORD '新密码';
```

完整改密码顺序：

1. 更新根 `.env` 的 `POSTGRES_PASSWORD`
2. 更新 `backend/.env.production` 的 `DATABASE_URL`
3. 上传两个文件，`chmod 600`
4. `docker compose up -d --no-deps --force-recreate db`（让 db 容器拿到新变量；数据卷不会丢）
5. 执行 `ALTER USER` 改数据库里的真实密码
6. `docker compose up -d --no-deps --force-recreate flask`（让 flask 用新 `DATABASE_URL`）
7. `docker compose exec -T flask alembic current` 验证能连库

**不要**用 `docker compose down -v`，`-v` 会删数据卷。

---

## 九、怎么验证变量存在（不打印值）

```bash
docker compose exec -T flask python -c "import os; print({k: bool(os.getenv(k)) for k in ['SECRET_KEY','JWT_SECRET_KEY','DEEPSEEK_API_KEY','DATABASE_URL']})"
```

输出全是 `True` 就说明注入成功。

想验证数据库连接：

```bash
docker compose exec -T flask alembic current
```

能输出 `817dbec35363 (head)` 就说明 `DATABASE_URL` 的新密码是对的。

## 十、安全边界

| 风险 | 现状 | 说明 |
|---|---|---|
| 密钥进 Git | ❌ 已避免 | `.gitignore` |
| 密钥进镜像 | ❌ 已避免 | `.dockerignore` |
| 宿主机文件被其他用户读 | ❌ 已避免 | `chmod 600` |
| `docker inspect` 看到环境变量 | ⚠️ 可见 | 能登录服务器并执行 docker 的人就能看 |
| 容器内进程读到密钥 | ✅ 必然 | 应用需要它，无法避免 |

`chmod 600` 保护的是"宿主机的文件"，不是"容器里的环境变量"。更高安全要求可以用 Docker secrets 或外部密钥服务；自用项目当前方案够用。

## 十一、常见坑

| 现象 | 根因 | 处理 |
|---|---|---|
| 改了 `.env.production` 但容器行为没变 | 只 `restart`，没重建容器 | `up -d --force-recreate 服务` |
| flask 连不上 db | `DATABASE_URL` 和 `POSTGRES_PASSWORD` 不一致 | 两个文件同步改 |
| 改了 `POSTGRES_PASSWORD` 还是旧密码 | 数据卷已存在，变量只在初始化时生效 | `ALTER USER` |
| `docker compose` 警告变量为空 | 不在项目根目录，找不到 `.env` | `cd /root/AIChat` 再执行 |
| 镜像里搜到密钥 | `.dockerignore` 没排除 `.env*` | 补 `.dockerignore` 并重建 |
| 把 `.env` 提交进 Git | `.gitignore` 漏了 | `git rm --cached` + 补规则 + 轮换密钥 |
| `docker compose config` 打印密钥 | 该命令会展开变量 | 不要在有日志/录屏的环境执行，或用 `--quiet` |

---

## 十二、一句话总结

**代码永远只认 `os.getenv()`；`.env` 和 `.env.production` 只是"谁负责把值塞进进程环境"的不同方式——本地是 python-dotenv，生产是 Docker Compose 的 `env_file`；根目录 `.env` 只负责 Compose 的变量插值；三者都不进 Git、不进镜像。**
