## 二、网络与镜像源（最重要的一类）

### 2.1 GitHub 不可达

**现象**：服务器上 `curl https://github.com` 返回 `000`，`git clone` 失败。

**根因**：服务器所在网络到 GitHub 的链路不可达。

**解决**：本机打包，通过 SSH 传到服务器：

```bash
tar -czf - --exclude=... backend frontend nginx docker-compose.yml \
  | ssh aichat 'tar -xzf - -C /root/AIChat'
```

**教训**：部署方案要假设"服务器不一定能访问所有外网"。源码传输、镜像拉取、npm 安装是三条独立的网络链路，任何一条断了都要有替代方案。

### 2.2 Docker 镜像 `not found`

**现象**：

```text
docker.io/library/python:3.13-slim: not found
docker.io/library/postgres:18-alpine: not found
```

**根因**：`/etc/docker/daemon.json` 里只配了一个不完整的阿里云个人加速器，它只有部分镜像的缓存，没有的就返回 not found；Docker 不会自动回退到 Docker Hub（直连也不可达）。

**解决**：

```json
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://xup15o5d.mirror.aliyuncs.com"
  ]
}
```

```bash
sudo systemctl restart docker
docker pull postgres:18-alpine
docker pull python:3.13-slim
docker pull node:22-alpine
```

**教训**：`registry-mirrors` 是**按顺序尝试**的；mirror 返回 not found 不代表 Docker 会继续找下一个/上游。用之前先 `docker pull` 验证关键镜像。

### 2.3 nginx 基础镜像过期

**现象**：`docker compose exec nginx nginx -v` 显示 `1.21.5`。

**根因**：之前用旧加速器拉过 `nginx:alpine`，本地 tag 指向旧镜像；`docker compose build` 直接用了本地旧镜像。

**解决**：

```bash
docker pull nginx:alpine
docker compose build nginx
docker compose up -d --no-deps nginx
docker compose exec nginx nginx -v   # 1.31.8
```

**教训**：浮动 tag（`alpine`、`latest`）不保证是最新版。生产环境应钉精确版本或 digest。

## 三、PostgreSQL 18 数据卷

**现象**：`./pgdata` 是空目录，但数据库正常工作。

**根因**：PG18 的 `PGDATA=/var/lib/postgresql/18/docker`，官方 `VOLUME` 是 `/var/lib/postgresql`；旧 compose 挂的是 `/var/lib/postgresql/data`，这个路径根本没被使用，数据进了匿名卷。

**解决**：

```yaml
volumes:
  - ./pgdata:/var/lib/postgresql
```

**验证**：

```bash
docker image inspect postgres:18-alpine --format '{{json .Config.Env}}'
docker image inspect postgres:18-alpine --format '{{json .Config.Volumes}}'
docker compose exec db psql -U aichat -d aichat -c "SHOW data_directory;"
```

**教训**：升级基础镜像大版本时，先看镜像的 Env 和 Volumes，不要照抄旧配置。这个坑不会报错，只会静默丢持久化。

## 四、npm 锁文件不完整

**现象**：

```text
npm error `npm ci` can only install packages when your package.json and
package-lock.json or npm-shrinkwrap.json are in sync.
Missing: @emnapi/core@1.11.3 from lock file
```

**根因**：本机 Node 24 / npm 11 生成的 lock，在 `@rolldown/binding-wasm32-wasi` 的可选依赖上只写了引用、没写包条目；容器的 npm 10 严格校验时拒绝。

**解决**：用 npm 10 重新生成 lock（显式 npmjs 源），验证 `npm ci --dry-run` 通过后替换、提交、上传、重建。

**教训**：
- 本地和构建环境的 npm 大版本尽量一致
- 不要让 Docker 改成 `npm install` 绕过锁文件
- 改 lock 后用 diff 确认只改了该改的

## 五、443 端口：为什么不能一步到位

**现象**：`curl https://域名` 报 `Couldn't connect`；服务器上 `grep "listen 443" nginx.conf` 没有输出。

**根因**：443 的 server 块需要证书文件；证书还没签发时写进去，nginx 启动/ reload 会失败，连 80 也一起挂。

**解决**：分两阶段：

1. 80 加 ACME location → 重启 → certbot 签发
2. 证书就位 → 加 443 + 301 → `nginx -t` → reload

**教训**：涉及"配置文件引用尚不存在的文件"时，先准备依赖，再启用配置。nginx 的 `-t` 是安全阀，reload 前必须跑。

## 六、SSH 配置重复 Host 块

**现象**：VS Code Remote-SSH 报"无法解析主机名"；终端 `ssh aichat` 也失败。

**根因**：`C:\Users\123\.ssh\config` 里有两个 `Host aichat`：

```sshconfig
Host aichat
  HostName aichat      # ← 第一个，错误

Host aichat
  HostName 120.x.x.x   # ← 第二个，正确
```

SSH 的规则是：**同一 Host 的多个匹配块，按顺序处理，每个选项以第一次出现的值为准**。所以 `HostName aichat` 生效，SSH 去解析一个叫 `aichat` 的主机名，失败。

**来源**：VS Code 的 "Add New SSH Host" 里输入了 `ssh aichat`，VS Code 把 `aichat` 当主机名写进了配置。

**解决**：删掉第一个块，只保留完整的 Host 配置。以后用 **"Remote-SSH: Connect to Host..."** 选择已有的 `aichat`，不要用 "Add New SSH Host"。

**教训**：SSH config 是"首次匹配优先"，不是"后者覆盖前者"。

## 七、PowerShell 的几个坑

这些不是项目问题，但会浪费大量时间。

| 现象 | 原因 | 解决 |
|---|---|---|
| `ls -la` 报参数不匹配 | `ls` 是 `Get-ChildItem` 别名 | `Get-ChildItem` / `dir`，或用 Git Bash |
| `curl -I` 提示输入 Uri | `curl` 是 `Invoke-WebRequest` 别名，`-I` 被当成 `-InformationAction` | `curl.exe -I` |
| `cmd1 && cmd2` 报语法错误 | Windows PowerShell 5.1 不支持 `&&`（PowerShell 7 才支持） | 分开执行，或用 Git Bash |
| 多行 `\` 续行逐行执行 | PowerShell 的续行符是反引号 `` ` ``，不是 `\` | 单行命令，或用 Git Bash |
| `tar -czf - | ssh ...` 解压失败 | PowerShell 5.1 把原生命令输出当文本，可能损坏二进制流 | 用 Git Bash；或 `tar` 成文件后 `scp` |
| `scp /e/...` 找不到文件 | `/e/` 是 Git Bash 的挂载路径 | PowerShell 用 `E:\...` |

**建议**：这个项目的 SSH、tar、Docker、Git 操作用 Git Bash；Windows 管理、Python 3.13 用 PowerShell。

## 八、SSH 空闲断连

**现象**：终端放一会儿不动，出现 `client_loop: send disconnect: Connection reset`。

**根因**：中间 NAT/路由器/运营商清理空闲 TCP 连接；SSH 默认不发应用层心跳。

**解决**：在 `~/.ssh/config` 的 Host 块里加：

```sshconfig
ServerAliveInterval 30
ServerAliveCountMax 3
```

**补充**：长时间构建（`docker compose build`）建议放 `tmux` 里跑，断线后还能 `tmux attach` 找回。

## 九、无害警告与交互提示

### 9.1 Compose 的 Bake/buildx 警告

```text
WARN Docker Compose is configured to build using Bake, but buildx isn't installed
```

Compose 想用 Buildx 的 Bake 并行构建，系统没装，自动退回经典构建器。**不影响构建结果**，可以忽略。

### 9.2 certbot 的 EFF 邮件询问

```text
Would you be willing ... share your email address with the Electronic Frontier Foundation?
(Y)es/(N)o:
```

回答 `N` 即可；或者在命令里加 `--no-eff-email` 跳过。和证书签发无关。

> 备注：我一度以为 certbot 4.0 移除了这个参数，实际仍然存在。遇到不确定的参数，先 `certbot certonly --help | grep ...` 查。

## 十、注册后不能登录（不是 bug）

**现象**：注册接口返回 201，但没有 token；登录返回 403。

**原因**：`feature/manual-approval` 分支的设计——新用户默认 `is_active=false`，必须管理员放行。

**操作**：

```bash
cd /root/AIChat
docker compose exec flask python admin.py list
docker compose exec flask python admin.py approve 用户名
```

**教训**：这不是部署故障，看到 403 先看返回的 `error` 内容（"账号待审核"）。

## 十一、切换会话后气泡顺序颠倒（应用层 bug）

**现象**：点开一个已有会话，最新的 AI 回复显示在最上面，用户消息反而在下面；发第二条消息后更乱。

**根因**：

- 后端 `/api/conversations/<id>` 用 `order_by(created_at.asc())` 返回（旧 → 新）
- 前端 `messages.value = res.data.messages.reverse()` 又反转一次（新 → 旧）
- 点开会话触发 `selectConversation`，于是历史倒序；新消息又追加到尾部

**修复**：

```python
.order_by(ChatHistory.created_at.desc(), ChatHistory.id.desc())
```

前端保留 `.reverse()`，后端倒序 → 反转后正好是正序；`page=1` 也从"最早 20 条"变成"最新 20 条"。

**注意**：这次改动一开始只加了 `id.desc()`，没把 `asc()` 改成 `desc()`，等于没修。提交信息写了"倒序"但代码还是升序，后来用 `git commit --amend` 修正并强推。

**教训**：改排序要同时看**主排序键**和**兜底键**；提交前 `git diff` 确认实际改动。

## 十二、AI 回复里混入 `https://example.com`（不是 bug）

**现象**：模型回复"有什么我可以帮 https://example.com 忙的吗？"

**排查**：

1. 查数据库，`chat_history` 里存的就是带 URL 的原文 → 不是前端/nginx 插入
2. 用相同参数直接调 DeepSeek API，返回里没有 URL → 不是代码固定拼接
3. 代码里没有任何加 URL 的逻辑

**结论**：模型幻觉。`example.com` 是 RFC 2606 保留的示例域名，训练数据里大量出现，模型偶尔会把它当占位符塞进句子。

**可选缓解**：

- 在 `messages` 最前面加 system prompt，明确"不要插入无关链接或占位域名"
- 显式设置 `temperature`（如 0.7）降低随机性
- 换更强的模型

**注意**：幻觉只能降低概率，不能根除；这不是部署链路的故障。

## 十三、排错方法论

这次能比较快定位，靠的是同一套顺序：

1. **先分层**：DNS / 安全组 / Docker 端口映射 / 进程监听 / 应用配置 / 业务代码
2. **每层用最小命令验证**：`nslookup`、`ss -tlnp`、`curl --resolve`、`nginx -t`、`docker compose ps`
3. **一次只改一层**：不同时改 DNS、nginx、compose，否则不知道哪个生效
4. **看日志原文**：`docker compose logs`、`journalctl`、certbot 的 `/var/log/letsencrypt/letsencrypt.log`
5. **不猜参数**：版本、默认值、路径都从镜像/文档/`--help` 确认

## 十四、一句话总结

这次踩的坑可以归成四类：

- **网络可达性**：GitHub、Docker Hub、npm 源，三条链路各自可能断
- **版本差异**：PG18 路径、npm 10/11、nginx 1.21/1.31、Node 22/24
- **配置与状态不一致**：只 build 没 up、restart 不换镜像、旧 dist、重复 SSH Host
- **依赖文件缺失**：`.dockerignore`、lock 里的可选依赖、证书文件

排错时先问自己："这个现象属于哪一类？"比直接改配置快得多。
