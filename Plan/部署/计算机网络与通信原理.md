## 一、数据怎么从浏览器到达服务器——五层套娃

浏览器构造了一个 HTTP 请求后，操作系统网络栈做的事：**像俄罗斯套娃，一层包一层，每层在上一层外面加一个头。**

```
┌─────────────────────────────────────────┐
│  以太网帧头 (14 B) + 帧尾 (4 B)          │  ← 数据链路层：局域网一跳内用 MAC 地址通信
│  ┌────────────────────────────────────┐ │
│  │  IP 头 (20 B)                       │ │  ← 网络层：IP 地址让路由器知道往哪转发
│  │  ┌────────────────────────────────┐ │ │
│  │  │  TCP 头 (20 B)                  │ │ │  ← 传输层：端口号 + 可靠性保证
│  │  │  ┌────────────────────────────┐ │ │ │
│  │  │  │  HTTP 请求文本              │ │ │ │  ← 应用层：浏览器和服务器才懂
│  │  │  │  GET / HTTP/1.1            │ │ │ │
│  │  │  │  Host: www.baidu.com       │ │ │ │
│  │  │  └────────────────────────────┘ │ │ │
│  │  └────────────────────────────────┘ │ │
│  └────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

每层只关心自己的事，下层把上层整体当成不透明的数据。TCP 不知道 HTTP 是什么，IP 不知道 TCP 是什么，网卡不知道 IP 是什么。

## 二、各层逐层拆解

### 应用层——HTTP 请求

浏览器构造的纯文本：

```
POST /api/chat HTTP/1.1          ← 请求行：方法 + 路径 + 协议版本
Host: localhost                   ← 请求头：键值对，携带附加信息
Content-Type: application/json
Authorization: Bearer eyJhbG...
                                  ← 空行（头结束）
{"message": "你好"}               ← 请求体：实际数据（GET 请求没有体）
```

### 传输层——TCP 段

操作系统在 HTTP 请求外面包一层 TCP 头：

```
┌──────────────────────────────┐
│      TCP 头（20 字节）         │
│  源端口：54321（随机临时端口）  │  ← 返回数据时找到浏览器进程
│  目标端口：443（HTTPS 默认）    │  ← 到达服务器后交给哪个程序
│  序列号：1001                  │  ← 对方按序重组 + 去重
│  确认号：0（首次连接）          │  ← 确认收到对方数据
│  标志位：SYN=1                 │  ← TCP 三次握手的第一次
│  窗口大小：65535               │  ← 告诉对方我一次最多收多少
├──────────────────────────────┤
│  TCP 数据体（HTTP 请求全文）    │
└──────────────────────────────┘
```

**端口**：一个 16 位数字（0-65535），网络程序在操作系统里注册。操作系统按目标端口号把收到的包分发给对应进程：

```
数据包到达 → 目标端口 80 → Nginx 进程
           目标端口 5000 → Gunicorn 进程
           目标端口 22 → SSH 服务
```

端口是贴在网络连接上的数字标签，不是电路里的物理路径。和路由表选择的"网络接口（网卡）"是完全不同的两个概念——接口 = 物理/虚拟硬件设备，端口 = TCP/UDP 数字标签。

### 网络层——IP 包头

IP 层在 TCP 段外面再包一层 IP 头：

```
┌──────────────────────────────────┐
│          IP 头（20 字节）          │
│  源 IP 地址：192.168.1.5          │  ← 你的电脑
│  目标 IP 地址：110.242.68.66      │  ← 百度服务器
│  协议：TCP（6）                   │  ← 上层是 TCP
│  生存时间（TTL）：64              │  ← 每经过一台路由器减 1
├──────────────────────────────────┤
│  TCP 头 + HTTP 请求（IP 包体）    │
└──────────────────────────────────┘
```

IP 层只管"从哪个地址到哪个地址"，TCP 只管"数据怎么可靠传输"——各干各的。

### IP 地址——网络中定位一台计算机

IP 地址是 32 个二进制位，写成四段十进制数。每台连网的计算机至少有一个 IP 地址。

一台计算机可以有**多个 IP 地址**，绑在不同的网络接口上：

```
你的计算机
├── 环回接口 (lo)          IP: 127.0.0.1       ← 自己访问自己
├── WiFi 网卡 (wlan0)      IP: 192.168.1.5     ← 局域网/互联网
├── Docker 网桥            IP: 172.18.0.1      ← Docker 内部网关
└── WSL 虚拟网卡           IP: 172.25.0.1      ← Windows ↔ WSL 通信
```

不会乱套——因为每个 IP 绑在各自的接口上，路由表决定从哪个接口发出。

### IP 地址的三类

| 类型 | 地址 | 谁知道 | 例子 |
|------|------|------|------|
| 环回地址 | `127.0.0.1` | 只有本机自己 | curl localhost |
| 私网地址 | `172.18.0.x`、`192.168.x.x` | 局域网内的设备之间 | Docker 内部网络 |
| 公网地址 | 云服务器公网 IP | 整个互联网 | 百度 `110.242.68.66` |

私网地址只在局域网内部有效，公网 IP 全球唯一。`localhost` 是 `127.0.0.1` 的人类可读名字——操作系统内核强制约定：发给 `127.0.0.1` 的包不出网卡，在机器内部直接环回。物理机制：内核里有一个叫"环回接口（loopback interface）"的虚拟网卡。

### 路由表——决定从哪个网卡发出

操作系统维护着一张路由表，记录了"目标网络 → 从哪个接口出去"：

```
目标网络            接口              下一跳
127.0.0.0/8         lo                自己内部
172.18.0.0/16       docker0           Docker 容器
192.168.1.0/24      wlan0             WiFi 下的邻居
0.0.0.0/0           wlan0             192.168.1.1（默认路由——扔给路由器）
```

`0.0.0.0/0` 匹配所有 IP 但优先级最低——不认识的目标全走默认路由，交给路由器处理公网。

**路由表读的是 IP 头的目标 IP 地址**，不看 HTTP 请求内容。路由表选的是**网络接口（哪个网卡）**，不是**端口**。

### DHCP——自动获取 IP 地址

DHCP（Dynamic Host Configuration Protocol）= 设备接入网络时自动获取 IP 的协议。

```
你的电脑（刚连 WiFi）：     "有人吗？我要一个 IP！"（广播）
路由器（DHCP 服务器）：      "给你 192.168.1.5，能用 24 小时。"
你的电脑：                  "收到，192.168.1.5 归我用了。"
```

三句话，一秒完成。DHCP 还给你的不止 IP 地址——同时告知子网掩码、默认网关、DNS 服务器地址。

DHCP 用 UDP 67/68 端口通信（不是 TCP），因为连 IP 都还没有，做不到 TCP 先握手。

### 数据链路层——以太网帧

WiFi 网卡不认识 IP 地址——网卡认识的是**以太网帧**，需要**MAC 地址**。

```
┌─────────────────────────────────┐
│        以太网头（14 字节）         │
│  目标 MAC 地址：下一跳路由器的物理地址│
│  源 MAC 地址：你 WiFi 网卡的物理地址 │
│  类型：IPv4 (0x0800)            │
├─────────────────────────────────┤
│  IP 头 + TCP 头 + HTTP 请求      │
├─────────────────────────────────┤
│         帧尾（4 字节 CRC 校验）   │
└─────────────────────────────────┘
```

**IP 地址和 MAC 地址的区别**：IP 地址对路由器有意义——路由器读 IP 头决定往哪个方向转发。MAC 地址是网卡出厂时烧在芯片里的物理唯一标识（48 位，前 24 位厂商代码 + 后 24 位序列号），只在局域网一跳内有效——两个设备直接用网线/WiFi 通信时需要。IP 是全局的，MAC 是本地的。

IP 地址是网络配置的（DHCP 动态分配，可以变），MAC 地址刻在硬件里永不变。路由器靠 IP 找到目标网络，局域网内靠 MAC 找到目标设备。各管各的层。

**如果全球都用MAC地址通信，互联网会在扩容的瞬间崩溃**。这并非技术无法实现，而是**数学和物理规律**决定的必然结果。

使用IP地址而不全盘使用MAC地址寻址的原因在于：**MAC地址是“扁平”的（无规律），而IP地址是“分层”的（有规律）**。我们可以从四个维度来理解这个设计：

**1. 寻址效率的“灾难”——路由表爆炸（核心原因）**
MAC地址由厂商烧录在网卡上，前24位是厂商编号，后24位是流水号。**它不包含任何地理位置或网络归属信息**。

- **如果用它全球寻址**：全球每台路由器都必须记住**数十亿个**MAC地址分别连接在哪个端口上。这就好比让全球每个快递站都记住地球上每一个人的具体长相，每次送件都要全盘扫描。
- **现实中的IP机制**：IP地址按国家、城市、运营商进行**聚合**（如`202.96.0.0/12`代表上海电信）。路由器只需记住“通往这个网段走这条路”，路由表仅几十万条，效率极高。用MAC地址，路由表会膨胀到天文数字，路由器内存和CPU瞬间耗尽。

**2. 身份与位置的“混淆”——无法移动**
MAC地址是设备的**固化“身份证”**（出生刻在硬件上），而IP地址是设备的**当前“居住地址”**。

- 如果你的笔记本电脑从北京带到纽约，MAC地址没变。如果全球用MAC寻址，互联网骨干网必须实时更新：“这个MAC现在跑到纽约去了”。这意味着每次设备移动，全球无数核心路由器都要同步更新路由信息，**网络震荡将永不停歇**。
- 而IP地址变了（从北京网段变为纽约网段），数据包只需根据IP前缀自动切换路径，底层完全不用关心你换没换网卡。

**3. 广播风暴的“毁灭”——二层网络无法做大**
局域网靠**广播（ARP协议）**来寻找MAC地址。如果全球是一个巨大的二层网络（所有设备都在一个广播域内）：

- 你发一个广播问“谁是某某MAC？”，这个请求会扩散到全世界所有联网设备。
- 数以亿计的广播包每秒都在全网泛滥，会瞬间耗尽所有带宽，这被称为**广播风暴**。因此，必须用**路由器（三层设备）**隔断广播域，而路由器只认IP地址，不转发广播包。

**4. 物理介质的“脱钩”——MAC属于特定硬件**
MAC地址是**数据链路层（以太网）**的概念，只适用于有线/无线局域网。而互联网运行在**光纤、4G/5G、卫星、串口线**等无数物理介质上。

- 如果依赖MAC地址，那所有物理介质都必须统一为以太网格式，这极大限制了技术创新。
- **IP协议（网络层）**就像一个“万能翻译器”，它跑在MAC之上，让底层无论用什么物理技术，上层都能统一用IP通信，实现了完美的**分层解耦**。

------

其实早期工程师曾想过用MAC做全球寻址（比如IPv6的EUI-64格式，将MAC嵌入IP），但最终因为**隐私安全**（暴露设备厂商和唯一ID）和上述路由问题而被抛弃。如今IPv6虽然地址极多，但依然保留了**分层前缀**（如国家/ISP前缀），绝不会变成扁平的MAC寻址。

## 三、完整发送链路——从浏览器到路由器

```
1. 浏览器构造 HTTP 请求

2. DNS 解析：www.baidu.com → 110.242.68.66

3. 操作系统网络栈：
   → TCP 段（源端口随机，目标端口 443）
   → IP 包（源 IP=192.168.1.5，目标 IP=110.242.68.66）
   → 查路由表：匹配 0.0.0.0/0 → 走 wlan0 接口 → 下一跳 192.168.1.1
   → 查 ARP 缓存：192.168.1.1 的 MAC 地址是什么？
   → 封装以太网帧（目标 MAC=路由器的 MAC）
   → WiFi 网卡转成无线电信号发出

4. 你家路由器收到：
   → 剥掉以太网头
   → NAT 转换：源 IP 192.168.1.5 → 公网 IP 123.45.67.89
   → 临时分配源端口 54321，记映射：端口 54321 → 192.168.1.5
   → 重新封装以太网帧 → 发给下一跳

5. 公网路由器逐跳转发（BGP 路由表）→ 到达百度

6. 百度处理 → 返回数据 → 公网路由器转发回来

7. 你家路由器收到返回包：
   → 目标端口 54321 → 查 NAT 映射 → "54321 → 192.168.1.5"
   → 目标 IP 改回 192.168.1.5

8. 操作系统网络栈：包到达 WiFi 网卡 → TCP 重组 → 拆出 HTTP 响应 → 交给浏览器
```

## 四、NAT——网络地址转换

私网 IP 只在局域网内部有效。互联网上的路由器不认识 `192.168.1.5`——看到目标 IP 为这些段的包直接丢弃。

NAT 让路由器把私网 IP 换成自己的公网 IP，同时用临时端口号追踪"这个回复属于哪个内网设备"。

```
出站：源IP 192.168.1.5 → 路由器换成 公网IP 123.45.67.89:54321（记映射）
入站：目标 123.45.67.89:54321 → 路由器查映射 → 还原为 192.168.1.5
```

全球有无数家庭用 `192.168.1.5`——互不冲突，因为它们不出门，各自在自家路由器的 NAT 后面。

## 五、DNS——域名系统

**DNS = 名字 → IP 地址的翻译服务，一个全球分布式、层级化的数据库。**

### 完整解析链——从敲回车到拿到 IP

浏览器输入 `www.baidu.com`，发起查询，逐层往下追：

```
1. 浏览器本地缓存
   "我最近访问过 www.baidu.com 吗？"
   → 缓存里有 → 直接返回 IP（查询结束）
   → 缓存里没有 → 往下

2. 操作系统 hosts 文件
   C:\Windows\System32\drivers\etc\hosts
   → 你自己手动配过吗？→ 没有 → 往下

3. DNS 递归解析器（你的路由器或 ISP DNS 服务器，如 114.114.114.114）
   "我不知道，但我帮你问。"
   → 先问根域名服务器：

4. 根域名服务器（全球 13 组，IP 写死在操作系统里）
   "www.baidu.com？我不管具体域名，但 .com 归那组管——这是它们的 IP。"
   → 返回 .com 顶级域名服务器的 IP

5. .com 顶级域名服务器
   "baidu.com？归百度的权威 DNS 管——这是它的 IP。"
   → 返回 baidu.com 权威 DNS 服务器的 IP

6. 百度权威 DNS 服务器
   "www.baidu.com → 110.242.68.66"
   → 返回最终 IP

7. 递归解析器把结果返回给浏览器，同时缓存一份（下次不问根了）
```

### 为什么是层级化的

全球几亿个域名，一台服务器存不下。每层只管自己下面一级：

```
根（.）
├── .com ← 顶级域名服务器
│   ├── baidu.com ← 百度权威 DNS
│   │   ├── www.baidu.com → 110.242.68.66
│   │   └── map.baidu.com → 110.242.68.67
│   └── google.com ← Google 权威 DNS
├── .org
├── .cn
└── ...
```

### 和 DHCP 的关系

DHCP 给你不止 IP 地址——同时告知 DNS 服务器地址（通常是 `192.168.1.1`——你家路由器，或者 `114.114.114.114`——运营商公共 DNS）。之后浏览器做任何 DNS 查询，都先找这个地址。**DHCP 给你"找谁问路"的地址，DNS 替你走过去问路。**

### DNS 故障诊断——QQ 能上但网页打不开

QQ 用的是腾讯服务器的公网 IP（硬编码在客户端里），不经过 DNS。网页打不开但 QQ 能上 → 网络连接本身是通的 → 问题一定在 DNS 解析层。浏览器直接敲 `http://110.242.68.66` 能打开百度，但敲域名打不开 → DNS 服务器挂了或响应超时。修法：把 DNS 从自动获取改成 `114.114.114.114` 或 `8.8.8.8`，绕开 ISP 的故障 DNS。

### Docker 内部 DNS——同一个机制，不同作用域

Docker compose 里 `proxy_pass http://flask:5000` 的 `flask` 走的是 Docker 内置 DNS（`127.0.0.11`），把服务名解析成容器内网 IP。和公网 DNS 完全同一套"名字→IP"的查找机制，只是作用域不同——Docker DNS 只在容器内部网络有效。

## 六、为什么家庭计算机不能直接当公网服务器

三条物理限制叠加，把家庭网络锁死在"只能出站"的角色上：

### 1. 运营商封 80/443 端口（HTTP 和 HTTPS 的默认端口）

运营商的路由器在比你家的路由器更高一层的位置——在小区/街道/区级机房。它们丢弃所有从公网入站的 80/443 端口的请求，数据包到不了你家光猫。你可以在自己路由器上配端口转发，但运营商在更上游已经拦了。

80 和 443 是 HTTP 和 HTTPS 的**全球默认端口**（RFC 标准写死的）。浏览器、证书签发机构、所有 HTTP 客户端都有硬编码的默认值——不写端口号就自动连这两个。封了它们，你就没法搭建一个"用户正常使用、浏览器正常认可"的网站。

换了其他端口（如 8080）技术上能绕过去，但：URL 变成 `http://aichat.com:8080`——极不专业；更致命的是，**Let's Encrypt 的 HTTP-01 验证必须走 80 端口**——用其他端口申请不了免费证书。证书本身不绑定端口，但拿证书的那一步必须经过 80 端口。另一个验证方式 DNS-01 不需要端口开放，但需要域名注册商提供 DNS API——前提是你得先有域名。

### 2. NAT 缺少入站映射

NAT 映射表的规则是"谁主动对外发请求，就给谁记一条"。外部的人没有事先建立映射，路由器不知道入站请求该转发给哪个内网设备，直接丢弃。

### 3. 动态公网 IP

家庭宽带的公网 IP 是运营商临时分配的——重启路由器就可能变。你的域名 A 记录刚指向 `123.45.67.89`，下次重启变成了 `123.45.68.100`，域名就指空了。

### 和云服务器的对比

三条限制云服务器全解决了：公网 IP 直接贴在网卡上（不需要 NAT）、80/443 端口默认开放、IP 静态不变且可绑定域名。99 元/年的学生机全打通。

## 七、总结——计算机网络的核心概念

| 层 | 协议/概念 | 核心问题 |
|------|------|------|
| 应用层 | HTTP | 请求和响应长什么样 |
| 传输层 | TCP、端口 | 数据怎么可靠送达，到了交给哪个程序 |
| 网络层 | IP、路由表、NAT | 怎么找到目标计算机 |
| 数据链路层 | 以太网帧、MAC 地址、ARP | 局域网内怎么找到具体设备 |
| 基础设施 | DHCP、DNS | IP 从哪来，域名怎么翻译成 IP |

这些知识全部是操作系统和计算机网络课程的核心内容。不是按教材顺序学的——是从 `docker-compose.yml` 里 Nginx 监听的 80 端口出发，沿数据流物理路径一路追到网卡的 MAC 地址，自然踩进了每一层。
