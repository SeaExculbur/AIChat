## 一、数据怎么从浏览器到达服务器——五层套娃

浏览器构造了一个 HTTP 请求后，操作系统网络栈做的事：**像俄罗斯套娃，一层包一层，每层在上一层外面加一个头。**

```
┌─────────────────────────────────────────┐
│  以太网帧头 (14 B) + 帧尾 (4 B)          │  ← 数据链路层：局域网一跳内用 MAC 地址通信
│  ┌────────────────────────────────────┐ │
│  │  IP 头 (20 B)                       │ │  ← 网络层：IP 地址让路由器知道往哪转发
│  │  ┌────────────────────────────────┐ │ │
│  │  │  TCP 头 (20 B)                  │ │ │  ← 传输层：端口号 + 可靠性保证
│  │  │  ┌────────────────────────────┐ │ │ │
│  │  │  │  HTTP 请求文本              │ │ │ │  ← 应用层：浏览器和服务器才懂
│  │  │  │  GET / HTTP/1.1            │ │ │ │
│  │  │  │  Host: www.baidu.com       │ │ │ │
│  │  │  └────────────────────────────┘ │ │ │
│  │  └────────────────────────────────┘ │ │
│  └────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

每层只关心自己的事，下层把上层整体当成不透明的数据。TCP 不知道 HTTP 是什么，IP 不知道 TCP 是什么，网卡不知道 IP 是什么。

## 二、各层逐层拆解

### 应用层——HTTP 请求

浏览器构造的纯文本：

```
POST /api/chat HTTP/1.1          ← 请求行：方法 + 路径 + 协议版本
Host: localhost                   ← 请求头：键值对，携带附加信息
Content-Type: application/json
Authorization: Bearer eyJhbG...
                                  ← 空行（头结束）
{"message": "你好"}               ← 请求体：实际数据（GET 请求没有体）
```

### 传输层——TCP 段

操作系统在 HTTP 请求外面包一层 TCP 头：

```
┌──────────────────────────────┐
│      TCP 头（20 字节）         │
│  源端口：54321（随机临时端口）  │  ← 返回数据时找到浏览器进程
│  目标端口：443（HTTPS 默认）    │  ← 到达服务器后交给哪个程序
│  序列号：1001                  │  ← 对方按序重组 + 去重
│  确认号：0（首次连接）          │  ← 确认收到对方数据
│  标志位：SYN=1                 │  ← TCP 三次握手的第一次
│  窗口大小：65535               │  ← 告诉对方我一次最多收多少
├──────────────────────────────┤
│  TCP 数据体（HTTP 请求全文）    │
└──────────────────────────────┘
```

**端口**：一个 16 位数字（0-65535），网络程序在操作系统里注册。操作系统按目标端口号把收到的包分发给对应进程：

```
数据包到达 → 目标端口 80 → Nginx 进程
           目标端口 5000 → Gunicorn 进程
           目标端口 22 → SSH 服务
```

端口是贴在网络连接上的数字标签，不是电路里的物理路径。和路由表选择的"网络接口（网卡）"是完全不同的两个概念——接口 = 物理/虚拟硬件设备，端口 = TCP/UDP 数字标签。

### 网络层——IP 包头

IP 层在 TCP 段外面再包一层 IP 头：

```
┌──────────────────────────────────┐
│          IP 头（20 字节）          │
│  源 IP 地址：192.168.1.5          │  ← 你的电脑
│  目标 IP 地址：110.242.68.66      │  ← 百度服务器
│  协议：TCP（6）                   │  ← 上层是 TCP
│  生存时间（TTL）：64              │  ← 每经过一台路由器减 1
├──────────────────────────────────┤
│  TCP 头 + HTTP 请求（IP 包体）    │
└──────────────────────────────────┘
```

IP 层只管"从哪个地址到哪个地址"，TCP 只管"数据怎么可靠传输"——各干各的。

### IP 地址——网络中定位一台计算机

IP 地址是 32 个二进制位，写成四段十进制数。每台连网的计算机至少有一个 IP 地址。

一台计算机可以有**多个 IP 地址**，绑在不同的网络接口上：

```
你的计算机
├── 环回接口 (lo)          IP: 127.0.0.1       ← 自己访问自己
├── WiFi 网卡 (wlan0)      IP: 192.168.1.5     ← 局域网/互联网
├── Docker 网桥            IP: 172.18.0.1      ← Docker 内部网关
└── WSL 虚拟网卡           IP: 172.25.0.1      ← Windows ↔ WSL 通信
```

不会乱套——因为每个 IP 绑在各自的接口上，路由表决定从哪个接口发出。

### IP 地址的三类

| 类型 | 地址 | 谁知道 | 例子 |
|------|------|------|------|
| 环回地址 | `127.0.0.1` | 只有本机自己 | curl localhost |
| 私网地址 | `172.18.0.x`、`192.168.x.x` | 局域网内的设备之间 | Docker 内部网络 |
| 公网地址 | 云服务器公网 IP | 整个互联网 | 百度 `110.242.68.66` |

私网地址只在局域网内部有效，公网 IP 全球唯一。`localhost` 是 `127.0.0.1` 的人类可读名字——操作系统内核强制约定：发给 `127.0.0.1` 的包不出网卡，在机器内部直接环回。物理机制：内核里有一个叫"环回接口（loopback interface）"的虚拟网卡。

### 路由表——决定从哪个网卡发出

操作系统维护着一张路由表，记录了"目标网络 → 从哪个接口出去"：

```
目标网络            接口              下一跳
127.0.0.0/8         lo                自己内部
172.18.0.0/16       docker0           Docker 容器
192.168.1.0/24      wlan0             WiFi 下的邻居
0.0.0.0/0           wlan0             192.168.1.1（默认路由——扔给路由器）
```

`0.0.0.0/0` 匹配所有 IP 但优先级最低——不认识的目标全走默认路由，交给路由器处理公网。

**路由表读的是 IP 头的目标 IP 地址**，不看 HTTP 请求内容。路由表选的是**网络接口（哪个网卡）**，不是**端口**。

### DHCP——自动获取 IP 地址

DHCP（Dynamic Host Configuration Protocol）= 设备接入网络时自动获取 IP 的协议。

```
你的电脑（刚连 WiFi）：     "有人吗？我要一个 IP！"（广播）
路由器（DHCP 服务器）：      "给你 192.168.1.5，能用 24 小时。"
你的电脑：                  "收到，192.168.1.5 归我用了。"
```

三句话，一秒完成。DHCP 还给你的不止 IP 地址——同时告知子网掩码、默认网关、DNS 服务器地址。

DHCP 用 UDP 67/68 端口通信（不是 TCP），因为连 IP 都还没有，做不到 TCP 先握手。

### 数据链路层——以太网帧

WiFi 网卡不认识 IP 地址——网卡认识的是**以太网帧**，需要**MAC 地址**。

```
┌─────────────────────────────────┐
│        以太网头（14 字节）         │
│  目标 MAC 地址：下一跳路由器的物理地址│
│  源 MAC 地址：你 WiFi 网卡的物理地址 │
│  类型：IPv4 (0x0800)            │
├─────────────────────────────────┤
│  IP 头 + TCP 头 + HTTP 请求      │
├─────────────────────────────────┤
│         帧尾（4 字节 CRC 校验）   │
└─────────────────────────────────┘
```

**IP 地址和 MAC 地址的区别**：IP 地址对路由器有意义——路由器读 IP 头决定往哪个方向转发。MAC 地址是网卡出厂时烧在芯片里的物理唯一标识（48 位，前 24 位厂商代码 + 后 24 位序列号），只在局域网一跳内有效——两个设备直接用网线/WiFi 通信时需要。IP 是全局的，MAC 是本地的。

IP 地址是网络配置的（DHCP 动态分配，可以变），MAC 地址刻在硬件里永不变。路由器靠 IP 找到目标网络，局域网内靠 MAC 找到目标设备。各管各的层。

## 三、完整发送链路——从浏览器到路由器

```
1. 浏览器构造 HTTP 请求

2. DNS 解析：www.baidu.com → 110.242.68.66

3. 操作系统网络栈：
   → TCP 段（源端口随机，目标端口 443）
   → IP 包（源 IP=192.168.1.5，目标 IP=110.242.68.66）
   → 查路由表：匹配 0.0.0.0/0 → 走 wlan0 接口 → 下一跳 192.168.1.1
   → 查 ARP 缓存：192.168.1.1 的 MAC 地址是什么？
   → 封装以太网帧（目标 MAC=路由器的 MAC）
   → WiFi 网卡转成无线电信号发出

4. 你家路由器收到：
   → 剥掉以太网头
   → NAT 转换：源 IP 192.168.1.5 → 公网 IP 123.45.67.89
   → 临时分配源端口 54321，记映射：端口 54321 → 192.168.1.5
   → 重新封装以太网帧 → 发给下一跳

5. 公网路由器逐跳转发（BGP 路由表）→ 到达百度

6. 百度处理 → 返回数据 → 公网路由器转发回来

7. 你家路由器收到返回包：
   → 目标端口 54321 → 查 NAT 映射 → "54321 → 192.168.1.5"
   → 目标 IP 改回 192.168.1.5

8. 操作系统网络栈：包到达 WiFi 网卡 → TCP 重组 → 拆出 HTTP 响应 → 交给浏览器
```

## 四、NAT——网络地址转换

私网 IP 只在局域网内部有效。互联网上的路由器不认识 `192.168.1.5`——看到目标 IP 为这些段的包直接丢弃。

NAT 让路由器把私网 IP 换成自己的公网 IP，同时用临时端口号追踪"这个回复属于哪个内网设备"。

```
出站：源IP 192.168.1.5 → 路由器换成 公网IP 123.45.67.89:54321（记映射）
入站：目标 123.45.67.89:54321 → 路由器查映射 → 还原为 192.168.1.5
```

全球有无数家庭用 `192.168.1.5`——互不冲突，因为它们不出门，各自在自家路由器的 NAT 后面。

## 五、DNS——域名系统

**DNS = 名字 → IP 地址的翻译服务。**

Docker compose 里 `proxy_pass http://flask:5000` 的 `flask` 走的是 Docker 内置 DNS（`127.0.0.11`），把服务名解析成容器内网 IP。浏览器访问 `www.baidu.com` 走的是全球 DNS 层级系统——本地缓存 → 路由器 → ISP DNS → 根域名服务器 → .com 顶级域服务器 → 百度权威 DNS → 返回 `110.242.68.66`。

同一个机制，不同作用域。Docker 服务名不是"域名"（不在公网 DNS 注册），但用了完全同一套"名字→IP"的查找机制。

## 六、总结——计算机网络的核心概念

| 层 | 协议/概念 | 核心问题 |
|------|------|------|
| 应用层 | HTTP | 请求和响应长什么样 |
| 传输层 | TCP、端口 | 数据怎么可靠送达，到了交给哪个程序 |
| 网络层 | IP、路由表、NAT | 怎么找到目标计算机 |
| 数据链路层 | 以太网帧、MAC 地址、ARP | 局域网内怎么找到具体设备 |
| 基础设施 | DHCP、DNS | IP 从哪来，域名怎么翻译成 IP |

这些知识全部是操作系统和计算机网络课程的核心内容。不是按教材顺序学的——是从 `docker-compose.yml` 里 Nginx 监听的 80 端口出发，沿数据流物理路径一路追到网卡的 MAC 地址，自然踩进了每一层。
