## 一、给 users 表加一个"是否放行"的字段

需求：注册后不立刻能用，要管理员放行。

### 1.1 加列还是建新表——三个问题定生死

拿到一个"属性"，问三个问题：

| 问题 | `is_active` 的答案 | 结论 |
|---|---|---|
| **基数**：一个用户对应几条这种数据？ | 1 条 | 同表 |
| **生命周期**：用户删了，它还有意义吗？ | 没意义 | 同表 |
| **访问模式**：会经常和用户一起查吗？ | 是（登录时必查） | 同表 |

**什么时候才该拆表**：一个用户对应**多条**记录（登录日志）、或者这个实体能独立存在（订单）。

**拆表的代价是实打实的**：
- 每次查状态都要 JOIN——就为了一个布尔值
- **数据一致性风险**：`users` 有这行、状态表没这行怎么办？两张表意味着可能产生"半条记录"，而这是你凭空给自己造出来的问题
- 多一张表的迁移、索引、维护成本

**一句话原则**：**1:1 的属性放同一行，1:N 的关系才拆表。**

### 1.2 为什么是布尔，不是 `status` 字符串

状态机每多一个状态，**每一个读它的地方都要多想一遍"这个状态怎么办"**。三态里的"已拒绝"其实等价于"这行不存在"——拒绝就是删掉那行，不需要第三种状态。

`is_active` 这个名字是 Flask-Login 里 `UserMixin` 的惯例名，将来若引入它语义一致，不冲突。

## 二、三层默认值：Python 层 vs 数据库层

```python
is_active = db.Column(db.Boolean, nullable=False, default=False, server_default=db.false())
```

四个参数一个都不能少。重点是后两个的区别：

```
default=False              ← Python 层。SQLAlchemy 构造 INSERT 时帮你填
server_default=db.false()  ← 数据库层。写进表结构（DDL），由数据库自己填
```

**看生成的 SQL 最清楚**：

```sql
-- default=False：Python 进程算好再传过去
INSERT INTO users (username, password_hash, is_active) VALUES ('alice', 'xxx', 0)

-- server_default：体现在建表语句里
CREATE TABLE users (
    ...
    is_active BOOLEAN DEFAULT 0 NOT NULL      ← 写进表结构了
)

-- 所以哪怕完全绕过 ORM，这样插也能work（数据库自己填 0）：
INSERT INTO users (username, password_hash) VALUES ('alice', 'xxx')
```

### 为什么这次两个都要写

要应对两种**不同的插入场景**：

| 场景 | 谁生效 |
|---|---|
| 走 ORM 注册新用户 | `default=False`——SQLAlchemy 填 |
| **迁移加列时**，表里已有数据 | `server_default`——让 DDL 能执行，顺便给已有行填上 False |

**第二种是硬性的**。不写 `server_default`，SQLite 直接拒绝：

```
Cannot add a NOT NULL column with default value NULL
```

原因很直白：SQLite 要在已有行上补一个 `NOT NULL` 列——**已有的行填什么？** 没有默认值就没法填，只能报错。

**连带效应**：`server_default` 把已有行填成了 False（未放行）——**所以迁移脚本里还得手动补一句 `UPDATE users SET is_active = TRUE`**，否则自己都进不去。

### 为什么是 `db.false()`，不是 `False`

`db.false()` 是**SQL 表达式**，SQLAlchemy 会按方言翻译。实测的 DDL：

```
SQLite      →  is_active BOOLEAN DEFAULT 0 NOT NULL
PostgreSQL  →  is_active BOOLEAN DEFAULT false NOT NULL
```

**为什么 SQLite 是 0 而 Postgres 是 false**：SQLite 根本没有原生布尔类型，历史上用整数 0/1；Postgres 有真正的 boolean，写 `0` 反而报类型错误。

**这就是"一份模型定义，两种数据库都能跑"的关键。**

### 可以带走的原则

> **约束应该由数据自己保证，而不是靠调用方自觉。**

- `default=False` 是**约定**——只有"走 SQLAlchemy"这条路才生效
- `server_default` 是**保证**——谁插入都逃不掉，哪怕手工 SQL、别的程序、将来的你自己

同一个道理贯穿整个数据库设计：**NOT NULL、外键约束都放在数据库层，而不是只靠应用层校验。** 因为应用会换、会被绕过、会有第二个入口——**表结构是最后一道防线**。

## 三、Alembic 的两个陷阱

### 3.1 autogenerate 生成的是"现实快照"，不是"可移植的意图"

模型里写的是可移植的 `db.false()`，但 Alembic 生成迁移时，会**按"当前连着的那个数据库"的方言把它编译成文本**——当时连的是 SQLite，编译出来是 `0`，于是它把这当成**死字符串**写进文件：

```python
# Alembic 自动生成的（错）
op.add_column('users', sa.Column('is_active', sa.Boolean(), server_default=sa.text('0'), nullable=False))
```

`sa.text('0')` 的含义是"**原样输出 0**"，不再有任何方言翻译。实测对比：

```
                    SQLite                          PostgreSQL
sa.text('0')    →   DEFAULT 0 NOT NULL          →   DEFAULT 0 NOT NULL      ✘
sa.false()      →   DEFAULT 0 NOT NULL          →   DEFAULT false NOT NULL  ✔
```

**Postgres 收到 `DEFAULT 0` 会给 boolean 列直接报错**（它的 boolean 不接受整数）。

> **一句话记住**：autogenerate 生成的是"**此刻数据库上的现实快照**"，不是"**可移植的意图**"。它把"能在我现在这台机器上跑通"当成了目标，而不是"在任何数据库上都正确"。

**这就是那两行注释在说的话**：

```python
# ### commands auto generated by Alembic - please adjust! ###
                                                  ↑ "请自行调整"
```

**autogenerate 给你的是草稿，不是成品。** 它自己都在提醒你——只是大多数人不看注释。

### 3.2 迁移文件必须"冻结在写它的那一刻"

**不要**在迁移里 `from models import User` 然后用 `User.is_active`。为什么：

三个月后你把模型里的 `is_active` 改名成 `status`——**这个老迁移脚本的行为会跟着变**：它跑去加一个叫 `status` 的列，而不是当时那个 `is_active`。**历史被改写了。**

> **迁移是历史的记录，不是当前状态的描述。** 所以它必须自带一份"当时的结构快照"，`sa.Column(...)` 就是那份快照。

### 3.3 schema migration vs data migration

| 术语 | 做什么 | 例子 |
|---|---|---|
| **schema migration**（结构迁移） | 改表的结构 | 加列、建表、加索引 |
| **data migration**（数据迁移） | 改表里的**内容** | 给已有行填值、拆分字段 |

**一个迁移文件里可以两者都有。** 对应到 API：

- DDL（CREATE/ALTER/DROP）→ 用 `op.add_column` / `op.create_table` 这类结构化 API
- DML（UPDATE/INSERT/DELETE）→ 用 `op.execute("原样 SQL")`

**为什么 Alembic 不自动写那句 UPDATE**：它看到的信息只有"模型里多了一个列"——至于"**已有的那些行该填什么**"，那是**业务决策**，不是结构信息。它能做的最安全的猜测就是填 False，而"老用户应该被放行"只有你知道。

## 四、`op` 是什么，以及迁移为什么只跑一次

### 4.1 `op` 是代理对象，不是普通模块

```python
from alembic import op
op.add_column('users', sa.Column(...))
```

**`op.add_column(...)` 不会立刻执行任何 SQL**，它做的是"登记一个意图"：

```
你写 op.add_column(...)
    ↓
Alembic 转成 SQLAlchemy 的 DDL 对象
    ↓
用【当前连着的数据库】的方言编译成 SQL
    ↓
执行
```

**为什么不直接写 SQL**：

| 直接写 SQL | 用 `op` |
|---|---|
| 锁死在一种数据库的语法上 | 方言无关，Alembic 按当前连接翻译 |
| Alembic 手里只有一坨字符串 | Alembic 手里有**结构化信息**（表名、列名、类型、约束） |

**"结构化信息"有什么用**：比如 SQLite 上要改列类型时，Alembic 得"建新表 → 拷数据 → 改名 → 删旧表"——它**必须知道表的完整结构**才做得成。

> 想查 `op` 后面能接什么，看 `alembic.operations.Operations` 这个类的 API 列表——那才是 `op` 背后的实现。

### 4.2 `upgrade()` 只跑一次——`alembic_version` 账本

Alembic 在数据库里建了一张表专门记账：

```
alembic_version
('817dbec35363',)      ← 当前这个数据库站在迁移链的哪个位置
```

`alembic upgrade head` 每次做的事：

```
① 读账本            → "现在是 817dbec35363"
② 沿 down_revision 链往后找 → 看后面还有没有新版本
③ 有 → 依次跑它们的 upgrade()；没有 → 什么都不做
```

所以 `upgrade()` **只会在"从上一个版本升到它"那一次被调用**。那句 `UPDATE users SET is_active = TRUE` 不会在你以后每次 upgrade 时重跑。

**你可以自己验**：再跑一次 `alembic upgrade head`，**不会有 `Running upgrade` 输出**——因为无事可做。

### 4.3 由此推出的一条铁律

> **迁移文件一旦在某个数据库上跑过，就不要再改它。**

因为它**不会被重跑**。你改了文件内容，数据库那边什么都不会发生。更糟的是**各环境的账本会对不上**：

```
本地库：按"旧版本的文件"跑出来的结构
生产库：按"新版本的文件"跑出来的结构
两边账本上都写着同一个 hash  ← 但实际结构不一样
```

**同一份代码，两个不同结构的数据库。** 这是最难查的一类问题。要修正已经跑过的迁移，**正确做法是新写一个迁移**。

### 4.4 两条命令的分工

```
① alembic revision --autogenerate -m "描述"    → 生成一个 .py 文件（只读数据库，不写）
② alembic upgrade head                        → 把库改了 + 更新账本
```

**中间必须留出人工检查的窗口**——生成出来的是草稿，要检查方言问题、补数据迁移。这就是"生成"和"执行"为什么必须分开。

**一个高频误解**：`alembic upgrade head` **不会读 models.py**，也不会自动生成新迁移。它只跑 `versions/` 目录里已存在的文件。所以**改了模型却忘了生成迁移**时，它会平静地说"已是最新版本"——而数据库里根本没有那个新列。

**判断依据**：输出里**没有 `Running upgrade A -> B`** 就说明它什么都没干。

### 4.5 一条命令背后的九步

跑 `alembic upgrade head` 时，实际发生的事：

```
① alembic.exe 启动 Python（venv 里的启动器）
② 读 alembic.ini：script_location（脚本在哪）+ sqlalchemy.url（连哪个库）
③ 执行 env.py：create_app() 建了整个 Flask 应用 + 手动 push app context
④ 连数据库 → 打印 "Context impl SQLiteImpl."
⑤ 读 alembic_version 账本
⑥ 沿链找待跑版本 → 打印 "Running upgrade A -> B"
⑦ 执行 upgrade() 里的每条 op
⑧ 更新账本
⑨ 退出
```

**第③步值得注意**：为了跑一条 `ALTER TABLE`，**你的整个 Flask 应用被初始化了一遍**（因为 autogenerate 需要 `db.metadata` 才能对比模型）。副作用：如果 `create_app()` 因为某个环境变量缺失而报错，**`alembic upgrade` 也会跟着失败**——哪怕这个迁移跟 Flask 一点关系都没有。

**第④步那行 INFO 的含义**：`impl` = implementation，Alembic 给每种数据库准备了一个"实现类"来处理差异。

**另一行 INFO 更值得留意**：

```
INFO  [alembic.runtime.migration] Will assume non-transactional DDL.
```

意思是"按'DDL 不会随事务回滚'来处理"：

| | DDL 能否随事务回滚 |
|---|---|
| **PostgreSQL** | ✔ 能。迁移失败自动回到干净状态 |
| **SQLite** | ✘ 不能（准确说：Python 的 pysqlite 驱动默认不在 DDL 前开事务，导致 DDL 被隐式提交） |

**对部署的含义**：本地 SQLite 上迁移失败会留下半成品，生产 Postgres 上会自动回滚。

### 4.6 为什么迁移文件必须进版本控制

**判断标准**：别人 clone 这个仓库，需不需要它才能把项目跑起来？

```
models.py                  ← 描述数据库【现在应该长什么样】      ✔ 进
alembic/versions/*.py      ← 描述【怎么从旧结构走到新结构】      ✔ 必须进
instance/aichat.db         ← 产物，每个环境自己长                ✘
venv/                      ← 产物，pip install 能重建            ✘
```

**迁移文件是"代码"，不是"产物"。** 缺了它，服务器上 `alembic upgrade head` 只能跑到建表那一步，**生产库没有 `is_active` 列**，应用一启动就报错——而且是"本地完全正常、服务器上必挂"的那种。

**同一个判断标准，四个不同结论**——判据是"**克隆下来跑不跑得起来、跑得对不对**"，不是"这个文件重不重要"。

## 五、Flask app context——CLI 脚本为什么必须手动 push

`admin.py` 里有一行看起来多余的东西：

```python
with app.app_context():
    ...数据库操作...
```

### 5.1 `db.session` 不知道自己属于谁

源码（`flask_sqlalchemy/session.py:109`）：

```python
def _app_ctx_id() -> int:
    """Get the id of the current Flask application context for the session scope."""
    return id(app_ctx._get_current_object())
```

```python
# extension.py:410
scope = options.pop("scopefunc", _app_ctx_id)
return sa_orm.scoped_session(factory, scope)
```

**session 的作用域是按"app context 的 id"划分的**。所以 `db.session` 每次被访问时：

```
① 问：当前的 app context 是哪个？   ← 没有 → RuntimeError
② 用它的 id 去查：这个作用域里已经有 session 了吗？
③ 有就返回那个，没有就新建一个
```

**没有 app context，第①步就炸**：

```
RuntimeError: Working outside of application context.
```

**准确的表述**：`with` 的作用不是"选择哪个 app"，而是"**建立当前环境**"——让 `db.session` 这种不知道自己是谁的对象，能查到"现在该依附于谁"。

### 5.2 两个 app 实例同时存在会怎样

```
db.init_app(app)          →  建立【绑定】：这个 db 属于这个 app
with app.app_context():   →  建立【当前】：现在这几行代码依附于哪个 app
```

**前者是静态关系，后者是动态标记。** `db.session` 需要的是后者。

因为 session 按 context id 划分作用域，所以两个不同的上下文里拿到的是**两个不同的 session**——各管各的事务、各用各的连接。这也解释了**为什么两个用户同时发请求不会互相踩**：他们的请求有各自独立的 app context，就有各自独立的 session。

### 5.3 push / pop 是栈，`with` 保证出栈

```python
def push(self) -> None:
    """Binds the app context to the current context."""
    self._cv_tokens.append(_cv_app.set(self))     # ↓ 绑定

def pop(self, exc):
    ...
    _cv_app.reset(self._cv_tokens.pop())          # ↑ 恢复原状
```

- `push()` 用 `ContextVar.set()` 绑定当前 context，并**留下一个 token**
- `pop()` 用那个 token **恢复**到之前的状态

**"留下 token 再恢复"意味着它是可嵌套的**：

```
push A   →  当前是 A
  push B →  当前是 B
  pop B  →  当前回到 A
pop A    →  当前回到"没有"
```

**这就是为什么用 `with` 而不是普通函数调用**——`with` 保证**退出时必然 pop**，哪怕抛异常退出。

### 5.4 app context 退出时还会"收摊"

```python
# extension.py:318（在 init_app 里注册的）
app.teardown_appcontext(self._teardown_session)

# extension.py:448
self.session.remove()
```

**退出 with 块时干了两件事**：

```
① pop 上下文       ← 取消"当前"这个标记
② 清理 session     ← 关闭 session、把数据库连接归还到连接池
```

**推论**：在块里查出来的对象，拿到块外面继续用有风险。如果访问某个还没加载的属性（需要再查一次数据库），会报：

```
DetachedInstanceError: Instance <User> is not bound to a Session
```

### 5.5 HTTP 请求里为什么你从来没写过这个 `with`

```python
@chat_bp.route("/api/conversations", methods=["GET"])
def list_conversation():
    convs = Conversation.query...       # ← 这里 db.session 也是要 app context 的
```

**Flask 在调用视图函数之前，会自动 push 一个 request context；而 push request context 时，如果当前没有 app context，它会顺带 push 一个**。源码里有直接证据：

```python
# flask/ctx.py:377  RequestContext.push()
def push(self) -> None:
    # Before we push the request context we have to ensure that there
    # is an application context.
    app_ctx = _cv_app.get(None)
```

**所以你写的每个视图函数都活在两层上下文里**（request + app），只是它们由框架自动 push、自动 pop，你从来没感觉到。

**CLI 脚本里没有请求**，Flask 的 `wsgi_app()` 根本没被调用过，没人帮你 push——**你得自己来**。（也解释了为什么 CLI 里只需要 app context：没有"请求"这个概念，也就不存在 `request` 对象可取。）

## 六、安全——公网开放前必须堵的洞

### 6.1 越权（IDOR）：客户端传来的 id 是"声明"，不是"事实"

```python
conversation_id = data.get("conversation_id")     # ← 客户端说多少就是多少

if conversation_id is None:
    ...新建...
# 否则：直接往下用 —— 没有任何检查
```

**攻击者 B 的利用方式**：

```
POST /api/chat
Authorization: Bearer <B自己的token>              ← 身份是真的
{"message": "垃圾内容", "conversation_id": 7}      ← 但会话 id 是 A 的
```

消息就被存进了 A 的会话（`user_id` 是 B、`conversation_id` 是 A 的），而 A 打开会话时——`get_conversation` 里查消息**只按 conversation_id 过滤**——**会看到 B 插进去的那条**。

**这类漏洞的本质，一句话**：

> **服务端把客户端传来的 id 当成了"事实"，而它其实只是一个"声明"。**

**通用的判断原则**：

```
客户端传来的任何东西 —— id、用户名、金额、角色 —— 都是【声明】
                      ↓
       必须拿它和"你是谁"（token 里的身份）做一次联合校验
                      ↓
        才能用它去查/改数据
```

**代码上的写法**：把它们绑在**同一次查询**里：

```python
Conversation.query.filter_by(id=conv_id, user_id=current_user_id).first()
# 查得到才是你的，查不到就 404
```

**顺带一条**：**"会话不存在"和"会话不属于你"要返回同一个 404**。别写成"这个会话不是你的"——那等于告诉攻击者"这个 id 存在，只是不归你"，是**信息泄露**。

**类比**：酒店房卡。你说"我要进 302 房"——前台必须核对你**是不是 302 的住客**，不能因为你能说出房间号就让你进。房号不是凭证，**身份 + 房号**才是。

### 6.2 用户枚举：登录报错不能区分两种情况

```python
if not user or not check_password_hash(user.password_hash, password):
    return jsonify({"error": "用户名或密码错误"}), 401
```

**"用户不存在"和"密码错误"必须合并成同一个回复**。否则：

- 报"用户不存在" → 攻击者能**逐个试出哪些用户名已被注册**（一个免费的用户名存在性查询接口）
- 报"密码错误" → 说明这个用户名**存在**

**顺带**：状态检查（账号是否放行）必须放在**密码验证之后**。反过来放，密码输错的人也能收到"账号待审核"——那又成了一个探测接口。**先证明"你是这个账号的主人"，再谈"这个账号能不能用"。**

### 6.3 认证 ≠ 授权

```python
@jwt_required()          # ← 只证明"你是某个用户"
def approve_user():      # ← 但任何人都可以是"某个用户"（自己注册一个就行）
```

**这是最常见的越权漏洞**：接口写了 `@jwt_required()` 就以为安全了，忘了校验**权限**。

```
认证（Authentication）= "你是谁"
授权（Authorization） = "你能做什么"
```

**两件事，必须分别做。**

### 6.4 最小攻击面：为什么手动放行用脚本，不用管理后台

| | 脚本 `admin.py` | 控制后台 |
|---|---|---|
| 怎么运行 | 在服务器上敲一行命令 | 任何能发 HTTP 请求的人都能**尝试**触发 |
| 网络暴露 | **零**——不监听任何端口 | 每个管理接口都是新入口 |
| 拿什么保护 | SSH 权限 | 代码里的鉴权逻辑（写错了就是漏洞） |

> **不需要网络入口的功能，就不要给它网络入口。**

**频率决定工具形态**：这是自己用的站，放行操作的总次数可能是个位数（分布在整个项目生命周期里）。为一个一辈子点几次的按钮建后台（角色字段、管理接口、鉴权、新页面、路由守卫、越权校验），工作量从十几行跳到几百行。

**而且**：管理接口是攻击者最优先扫描的目标——你的站上会多出 `/api/admin/...` 这样一个高权限路径，而它保护的只是一个你自己都不怎么用的功能。

**判断方式**：**每开一个入口，就得为它永久负责**——写鉴权、测越权、跟着业务变化维护。脚本没有这个负担。

### 6.5 死代码最危险的地方：它掩盖了旁边的错误

```python
if not change_password:                          # ← 判的是【函数对象】，永远为真
    logger.warning("...", user_id)               # ← user_id 这时还没赋值 → NameError
    return jsonify("新密码不能为空")
oldpassword = data.get("old_password")
user_id = int(get_jwt_identity())                # ← 第 84 行才赋值
```

**两层套娃**：
- 第一层：判断对象写错了（判的是函数名，不是变量名）→ 分支**永远不执行** → 死代码
- 第二层：那个分支**如果真的执行**，会立刻 `NameError: name 'user_id' is not defined`

**但它从来没被执行过**——所以第二个 bug 一起被埋了。

> **死代码最大的危害不是"占地方"，而是它掩盖了旁边的错误。** 如果那段代码是活的，第一次测试就会看到 NameError，五分钟修好。

**还有第三层**：`jsonify("裸字符串")` 会返回 **HTTP 200**（body 是一个 JSON 字符串）——**用成功状态码返回一个错误**，前端会去找 `response.data.error`（找不到）。

**为什么这个 bug 能活这么久**：因为 `if not change_password` **一眼读起来像"如果新密码为空"**——它符合你的预期，所以你不会怀疑它。**读代码时，大脑按"我以为它是什么"来理解，而不是按"它实际是什么"。只有执行不会骗你。**

### 6.6 fail-fast：安全配置的默认值应该是"启动失败"

```python
JWT_SECRET_KEY = os.getenv("JWT_SECRET_KEY", "dev-jwt-secret")
#                                          ↑ 没有环境变量时，用它
```

如果部署时漏传了环境变量，它**不报错**，直接拿一个**公开写在代码里**的密钥跑起来——而 JWT 的安全性完全建立在"只有我知道签名密钥"上，**密钥一旦是公开的，任何人都能伪造 token 冒充任何用户**。

**原则**：安全配置的默认值应该是"**启动失败**"，而不是"**降级到一个弱值**"。

**类比 C**：未初始化的指针——你希望程序**立刻崩**，而不是拿一个随机地址继续跑下去。

### 6.7 Docker 镜像层：`COPY` 进去的文件，后面删掉也没用

`Dockerfile` 里这一行会把**构建上下文的所有文件**复制进镜像：

```dockerfile
COPY . .        # ← .dockerignore 没挡住的东西，全进来
```

**为什么"后续层删掉也没用"**：Docker 镜像是**分层的只读存档**。`COPY . .` 把文件写进那一层之后，你在后续层 `RUN rm .env.production`——**那个文件仍然躺在历史层里**，任何人 `docker save` 导出后解包就能拿到。

**这跟 Git 里删掉密钥但提交历史还在，是同一个性质的问题。**

**修法**：`.dockerignore` 里写 `.env*`。

**注意 `.dockerignore` 的匹配语义**：

```
.env      ← 精确匹配这个名字的文件，【不匹配】.env.production
.env*     ← 通配，匹配所有 .env 开头   ✔
```

**而且**：`.dockerignore` / `.gitignore` 都**只管"未来"的操作**——改它不能修复已经构建好的镜像，也不能让已跟踪的文件从 git 里消失。

### 6.8 其他几条

- **资源耗尽型 DoS**：密码哈希（Werkzeug 默认 scrypt）的计算量**和输入长度相关**，一个超长密码会把一次请求的 CPU 时间拉得很长。所以密码要有**上限**（比如 128 字符）
- **日志注入**：用户名里含 `\n` 会**伪造出假的日志行**（CWE-117）。限制字符集有真实的安全意义
- **别图省事把 CORS 写成 `"*"`**：那等于允许任何网站带着用户的浏览器向你的 API 发请求
- **`.gitignore` 对已跟踪文件无效**：文件一旦进过仓库，写多少遍 `.gitignore` 都拦不住它。要真正取消跟踪得用 `git rm --cached`（`--cached` = 只从索引删，工作区文件不动）
- **exit code 是给脚本看的**：CLI 工具"操作失败"应返回非零码，方便 `admin.py approve x && echo ok` 这类判断

## 七、Git：暂存区 ≠ 跟踪

### 7.1 两件不同的事

| | 暂存（staged） | 跟踪（tracked） |
|---|---|---|
| 回答的问题 | **这次提交**要不要带上它？ | 这个文件**归不归** git 管？ |
| 命令 | `git restore --staged <文件>` | `git rm --cached <文件>` |
| 效果 | 从暂存区拿出来，改动**还在** | 文件**从仓库里消失** |
| 时效 | 一次性 | 长期 |

**"这次先不提交" ≠ "以后都不要它"。**

**判断标准**：**别人克隆这个仓库时，需不需要这个文件？**

- `.dockerignore` → **需要**（否则构建行为不同、密钥会进镜像）→ 必须跟踪
- `CLAUDE.md` → 个人工作约定 → 可以取消跟踪
- `venv/` → 不需要，能重建 → `.gitignore` 挡住

### 7.2 `git status --short` 的两列

```
XY 文件路径
││
│└─ 第二列：工作区相对【暂存区】的状态
└── 第一列：暂存区相对【上次提交】的状态
```

| 输出 | 含义 | 会进这次提交吗 |
|---|---|---|
| `A  file` | 暂存区里是"新增" | ✅ |
| `M  file` | 暂存区里是"修改" | ✅ |
| ` M file` | 只改了工作区，**没暂存** | ❌ |
| `?? file` | 未跟踪 | ❌ |

**一眼扫完**：**第一列有字母的 = 会进这次提交**。（`M ` 和 ` M` 差一个空格的位置，含义完全相反。）

**每次 commit 前跑一次 `git status --short`**——这是唯一能拦住手滑的步骤。

### 7.3 路径参数是相对"当前工作目录"的

```bash
# 你站在 backend/ 里
git add backend/requirements.txt
# → fatal: pathspec 'backend/requirements.txt' did not match any files
#   因为它找的是 backend/backend/requirements.txt
```

**同一个规则出现在别处**：`alembic.ini` 里的 `sqlite:///instance/aichat.db` 也是相对路径——**相对于你敲命令时所在的目录**解析，所以必须在 `backend/` 下跑迁移。

> **所有命令行工具接收的相对路径，基准都是"当前工作目录"，不是"文件所在位置"，也不是"仓库根"。**

**容易混的一点**：

```
git 命令能在 backend/ 里跑     ← 因为 git 会向上找 .git 目录，找到仓库根
但路径参数仍以当前目录为准      ← 这两个是【不同】的基准
```

### 7.4 僵尸规范：规范要么执行，要么删掉

项目 CLAUDE.md 里写着"**message 用英文祈使句**"，但 33 条提交历史里**只有 1 条是英文**——而且那条规范从**第一条提交**就在文件里了。

**成因**：规范很可能是从模板/教程/某次 AI 对话里**抄来的**，不是权衡后的决定。所以写 message 时按中文习惯走，规范躺在文件里没人看。

**为什么它比"没有规范"更糟**：**它会误导读它的人**。这次的实际影响已经发生了——AI 助手在给 commit 方案时，就是按"英文祈使句"设计的。

**处理**：改规范（一行字），别改历史（33 条 rebase 改 hash，风险高收益低）。

> **规范要么被执行，要么删掉，不要挂着。**

### 7.5 `git add .` 的危险

工作区里躺着没做完的文件时，`git add .` 会把它们**一起打包进提交**。这是"每次 commit 只做一件事"最容易被破坏的地方。

**更隐蔽的是 `git commit -a`**：它只加**已跟踪**文件的改动——所以会出现"**该带的没带、不该带的带了**"的组合。

**安全习惯**：

```
改代码 → git add <逐条列出的文件> → git status --short 核对 → git commit
```

## 八、环境与依赖

### 8.1 venv 的隔离机制

`pyvenv.cfg` 里两行关键信息：

```ini
home = E:\Python                          ← 基础解释器在哪
include-system-site-packages = false      ← 看不到全局的包（隔离生效）
```

**venv 里的 `python.exe` 只有几百 KB，不是复制了一份 Python**——它是个"知道自己属于哪个 venv"的启动器，标准库仍从 `home` 读。

**为什么要有虚拟环境**：Python 的包默认装在**一个全局目录**里，所有项目共用。项目 A 要 Flask 2.x、项目 B 要 Flask 3.x → 后装的覆盖先装的 → 一个项目必然崩。**venv 的本质就是给你一份独立的 `site-packages` 目录。**

**标准做法：每个项目一个 venv。**

### 8.2 解释器是"按项目"选的

- **VSCode**：选解释器是记在**工作区**的，换项目就换一套
- **命令行**：venv 里的 `python.exe` **只有在激活后才顶替 PATH**；**每开一个新终端窗口都是没激活的**——裸写 `python` 就是全局那个。所以推荐写完整路径 `venv/Scripts/python.exe`
- **物理上**：`backend/venv/` 只存在于这个项目里，别的项目看不到

### 8.3 "能跑但跑在错误环境"比"跑不起来"更危险

如果全局环境是**干净的**，敲 `python app.py` 会立刻 `ModuleNotFoundError: No module named 'flask'`——**错误当场暴露**。

但全局环境**恰好也装了一套** flask/sqlalchemy/openai，于是：

```
你敲 python app.py
    ↓
全局环境有 flask → 不报错 → 服务起来了
    ↓
你以为在跑 venv，其实跑在全局环境上，用的是 openai 2.36 而不是 venv 的 2.48
```

> **一个"能跑但跑在错误环境"的配置，比"跑不起来"更危险——因为前者不会报错。**

（这和 fail-fast 是同一个主题：**让错误尽早、显性地暴露**。）

### 8.4 依赖锁版本：`>=` 的代价

原来的 requirements.txt 全是下限约束：

```
openai>=1.58          ← 今天装会得到 2.48.0（跨了大版本 1.x → 2.x）
flask>=3.1
```

**后果**：同一个 `requirements.txt` 在不同时间装出来的环境**可能不一样**。最要命的是部署时——`docker build` 会在容器里**重新装一遍**，如果那时 PyPI 上又有新版本，容器里的环境和本地就**不是同一套**。

**解法**：`pip freeze > requirements.txt`，全部锁成 `==`。

**代价**：文件变长（含传递依赖），且失去"哪些是我直接用的"这个信息——将来升级要重新 freeze。**但这个代价换来的确定性值得**：生产环境要的是"装出来的东西一模一样"，不是"文件好看"。

**边界**：锁版本锁的是"**版本号**"，不是"同一个二进制"——同一版本号在 Windows 和 Linux 上是**不同的 wheel 文件**。

### 8.5 wheel 的平台差异与 slim 镜像

本地装的是 `psycopg2_binary-2.9.13-cp313-cp313-win_amd64.whl`，容器里会拿 `manylinux2014_x86_64` 那个。

**为什么必须验证 Linux 轮子存在**：`python:3.13-slim` 里**没有 gcc、没有 libpq-dev**。如果 Linux 上没有预编译轮子，pip 会退化成"下载源码编译"→ **缺编译器 → `docker build` 直接失败**。

（`cp313` 表示 CPython 3.13 的 ABI；`musllinux` 那个是给 Alpine 用的。）

### 8.6 本地 SQLite 宽容，Postgres 较真

这次撞到的几处，本质是同一类：

| | SQLite | PostgreSQL |
|---|---|---|
| VARCHAR 长度 | **不强制**（200 字符也能存） | 强制（报 `value too long`） |
| boolean 默认值 | `DEFAULT 0` ✔ | `DEFAULT 0` **报错**，必须是 `false` |
| 外键约束 | **默认关闭**，静默留孤儿行 | 强制，直接 `IntegrityError` |
| 迁移失败 | 留下半成品（非事务性 DDL） | 自动回滚 |

> **本地能跑 ≠ 生产能跑。** 这些差异全部是"本地测不出来、部署那天才发现"的类型。

### 8.7 镜像源与编码

- **清华源对这台机器整体 403**（flask / requests / psycopg2-binary 全一样），阿里云和腾讯云源 200 ✔
  - **诊断方法**：`curl -s -o /dev/null -w "%{http_code}" <源>/simple/<包名>/`，**并且拿一个确定存在的包做对照**（不然分不清"源挂了"和"包不存在"）
- **Windows 上 Python 默认用系统编码（GBK）写 stdout** → 在 Git Bash（按 UTF-8 读）里显示成乱码。解法：`PYTHONUTF8=1`

## 九、云服务器与备案（认知已建立，尚未落地）

### 9.1 云服务器的三笔账

```
① 实例（CPU + 内存）        ← 你买的"2核2G"就是这一项
② 云盘（系统盘 + 数据盘）
③ 公网带宽 / 公网 IP        ← 单独计费，可以完全是 0
```

**公网 IP 不是默认赠送的**，它是第三笔独立的账。特价机和免费试用机为了压价格，砍掉的往往就是这一项。

### 9.2 怎么判断一台机器有没有公网 IP

```bash
curl http://100.100.100.200/latest/meta-data/eipv4          # 空 = 没有
curl http://100.100.100.200/latest/meta-data/private-ipv4   # 私网地址（172.16.0.0/12 是阿里云私网段）
ip -4 addr show | grep inet
```

`100.100.100.200` 是阿里云的**元数据服务**——实例内部的"自我查询"接口，走内网，不需要公网。AWS 上的对应物是 `169.254.169.254`。

### 9.3 内网可达 ≠ 公网可达

| 操作 | 走哪条路 | 没有公网 IP 时 |
|---|---|---|
| `apt install` | 阿里云的**内网**镜像（`mirrors.cloud.aliyuncs.com`），走 VPC | ✔ 通 |
| `pip install` | 内网 PyPI 镜像 | ✔ 通 |
| `docker pull` | Docker Hub（**公网**） | ✘ 超时 |
| 公网访问你的网站 | 需要**入方向** | ✘ 不可能 |

**内网通、公网不通**这个组合，是"机器没有公网出口"的典型特征。

（顺带：`docker save` → 传文件 → `docker load` 可以完全绕开网络搬运镜像；但"网站被公网访问"这件事**绕不开**，必须有公网 IP。）

### 9.4 ICP 备案的机制

- **备案登记的是三样东西的联合关系**：主体（你是谁）+ 域名（服务叫什么）+ 接入（服务跑在哪条线路上）
- **必须通过接入服务商提交**——没有服务器 ≠ 没有接入商 ≠ 没有提交入口。**所以"先备案域名、再买服务器"这条路走不通**
- **备案服务号**：接入商给你的凭证（证明这个域名确实跑在他家机器上），从买的实例上申请
- **提交地域**：主流口径是**按主体（身份证所在地/实际居住地）选**，不是按服务器地域
- **跨省备案**（备案省份 ≠ 服务器所在省）：**是否允许由各省管局自定**
- **各省规则差异极大**：有的省要求"证件住所需为本省"（非本省要居住证/社保），有的省直接"非本省身份证不受理"。**只有身份证所在地和备案地一致时材料最省**
- **域名必须在工信部批复的顶级域列表里**，且**境外注册商的域名不能直接备案**（要先转入国内注册商）
- **个人备案一次只能提交 1 个域名**；域名有效期 > 30 天；域名持有者必须与主办人一致
- **通过后还要办"公安联网备案"**（30 日内），这是很多人漏掉的一步
- **合规边界**：面向公众提供生成式 AI 服务是另一套手续，个人主体走不通。所以"自用、不公开推广"这个定位同时决定了防白嫖措施和备案口径

| 1 | `/api/chat` 不校验会话归属 | **安全（越权）** |

| 7 | `Register.vue` 的 `localStorage.setItem('token', undefined)` | 手动放行的收尾 |

**关于第 7 条**：`localStorage.setItem` 不报错，它把 `undefined` 存成**字符串 `"undefined"`**（localStorage 只能存字符串）。而路由守卫只判 `!token`——`"undefined"` 是真理值 → 放行进 `/chat` → 请求带 `Authorization: Bearer undefined` → 401 → 跳回登录。**用户看到的现象是"注册成功后闪一下聊天页又被踢回来"。**

### 一个反复出现的主题

这次撞到的问题，背后是**同一条原则**在不同层面的表现：

```
改配置不会自动生效    →  必须执行命令让【现实】对齐【声明】
autogenerate 的快照    →  工具记录的是"当前现实"，不是"你的意图"
迁移文件不能改         →  它是历史，历史不能被重写
.gitignore 拦不住已跟踪文件  →  规则只管"还没进门的"
死代码掩盖 NameError   →  不执行的代码不会暴露问题
能跑但环境错           →  没有报错的地方，问题最难发现
```

> **规则/配置/工具给你的东西，要看清它到底记录了什么、在什么条件下才生效。**
