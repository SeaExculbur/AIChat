## 一、解决了什么问题

之前用户所有聊天记录混在一起——只有一个聊天窗口，没有"新建会话"的概念。现在用户能创建多个独立会话，左侧会话栏切换，每个会话有自己的历史记录。

## 二、数据模型

### Conversation 表

```python
class Conversation(db.Model):
    __tablename__ = "conversations"

    id = db.Column(db.Integer, primary_key=True)
    user_id = db.Column(db.Integer, db.ForeignKey("users.id"), nullable=False, index=True)
    title = db.Column(db.String(80), nullable=True)
    created_at = db.Column(db.DateTime, server_default=db.func.now())
    updated_at = db.Column(db.DateTime, server_default=db.func.now(), onupdate=db.func.now())
```

| 列 | 为什么 |
|------|--------|
| `title` | 会话标题——第一条消息的前 20 字自动填充。`nullable=True` 允许创建时暂时为空 |
| `updated_at` + `onupdate` | 每次在该会话发消息时自动刷新——会话列表按此排序，最近用的排最上面 |

### ChatHistory 加 conversation_id

```python
class ChatHistory(db.Model):
    ...
    conversation_id = db.Column(db.Integer, db.ForeignKey("conversations.id"), nullable=True, index=True)
```

| 参数 | 为什么 |
|------|--------|
| `ForeignKey("conversations.id")` | INSERT 时检查 conversation_id 在 conversations 表里真实存在 |
| `nullable=True` | 加列前的旧消息不属于任何会话——设为 None 兼容老数据 |
| `index=True` | `WHERE conversation_id=5` 走非聚簇 B+ 树，不全表扫描 |

**chat_history 表上的三棵 B+ 树**：

| 索引 | 类型 | 叶子存什么 | 谁在用 |
|------|------|-----------|--------|
| 主键 id | 聚簇 | 整行数据 | `get(id)` |
| user_id | 非聚簇 | (user_id → id) | 全局历史查询 |
| conversation_id | 非聚簇 | (conversation_id → id) | 会话内消息查询 |

`WHERE conversation_id=5` 直接走第三棵树，和 `conversations` 表无关。外键约束只在 INSERT 时检查一次。

## 三、后端接口

```
POST /api/chat  {message, conversation_id?}  → 流式聊天（自动创建会话）
GET  /api/conversations                       → 会话列表（左侧栏）
GET  /api/conversations/<id>                  → 某会话聊天记录（分页）
DELETE /api/conversations/<id>                → 删除会话 + 所有消息
```

没有 `POST /api/conversations`——会话在后端自动创建，前端不调创建接口。

### 3.1 聊天接口改动：自动创建会话

```python
conversation_id = data.get("conversation_id")

if conversation_id is None:
    title = user_message[:20]
    conv = Conversation(user_id=current_user_id, title=title)
    db.session.add(conv)
    db.session.commit()
    conversation_id = conv.id
```

`conv.id`：`commit()` 后 SQLite 自动分配自增主键，SQLAlchemy 填回 `conv.id`。

三处关联改动：

| 位置 | 原代码 | 改后 |
|------|--------|------|
| 查历史 | `filter_by(user_id=...)` | `filter_by(user_id=..., conversation_id=conversation_id)` |
| 存用户消息 | `ChatHistory(user_id=...)` | 加 `conversation_id=conversation_id` |
| 存 AI 回复 | 同上 | 加 `conversation_id=conversation_id` |

第一个 SSE chunk 返回 conversation_id：

```python
yield f"data: {{\"conversation_id\": {conversation_id}}}\n\n"
```

前端拿到后判断：如果左侧栏没有这个 id → 新会话 → 插入列表顶部。

### 3.2 会话列表

```python
convs = Conversation.query.filter_by(user_id=current_user_id) \
    .order_by(Conversation.updated_at.desc()).all()
```

`desc()` → 最近用过的会话排最上面。`updated_at` 由 `onupdate` 自动维护——你发消息时不需要手动刷。

### 3.3 某会话聊天记录

```python
conv = Conversation.query.filter_by(id=conv_id, user_id=current_user_id).first()
if not conv:
    return 404
```

**行级权限校验**：WHERE 条件同时验证 `id=conv_id` 和 `user_id=current_user_id`。用户 8 请求会话 3（属于用户 5）→ `id=3, user_id=8` → 0 行匹配 → 404。

分页逻辑和 `/api/history` 完全一样，`filter_by(user_id=...)` 换成 `filter_by(conversation_id=conv_id)`。

### 3.4 删除会话

```python
ChatHistory.query.filter_by(conversation_id=conv_id).delete()  # 先删消息
db.session.delete(conv)                                         # 再删会话
db.session.commit()
```

同 `delete_account`——先解外键依赖，再删主记录。不能反。

## 四、前端交互时序

```
页面加载
  → GET /api/conversations → 渲染左侧会话列表
  → 默认进入最新会话 → GET /api/conversations/<id>?page=1 → 渲染右侧聊天框

用户输入第一条消息（无 conversation_id）
  → POST /api/chat {message, conversation_id: null}
  → 后端自动创建会话 → 第一个 yield: conversation_id
  → 前端收到 → 左侧栏多一条 → 当前会话 id 设为新 id

用户在已有会话发消息
  → POST /api/chat {message, conversation_id: 5}
  → 前端收到第一个 yield: conversation_id=5
  → 前端判断 5 已存在 → 左侧栏把这条拖到最上面（本地排序，不请求后端）

用户往上翻历史
  → 滚动到顶 → ?page=2 → 加载更早的 20 条
  → 继续翻 → page++ → 直到 page >= pages

用户切换会话
  → GET /api/conversations/<id>?page=1 → 清空右侧 → 渲染新会话的聊天记录
```

## 五、代码优化

### DRY 分页：提取 paginate_query()

```python
def paginate_query(query):
    page = request.args.get("page", 1, type=int)
    per_page = request.args.get("per_page", 20, type=int)
    return query.paginate(page=page, per_page=per_page, error_out=False)
```

四行重复代码缩成一次函数调用。`query` 参数是一个 Query 对象——SQLAlchemy 的未执行查询计划。

### 注释原则

```python
# 会话列表(左侧栏)
# 某会话聊天记录(右侧聊天框)
# 删除会话
```

注释只解释**代码没说清的东西**——这个接口在前端的哪个位置被调用。参数和返回值代码本身已说清，不需要注释。

## 六、Response 与生成器深入

### Response 接受三种类型

```python
return Response("字符串")           # 一次性发送
return Response(["a", "b", "c"])    # 逐块发送
return Response(generate(), ...)    # 生成器逐块发送
```

Werkzeug 内部做判断——`isinstance(str)` → 一次 TCP write，否则 `for chunk in` → 多次发送。

### `return Response(generate(), ...)` 的时序

1. `generate()` 创建生成器对象——**一行代码没执行**
2. `return` 把生成器交给 Response
3. `chat()` 函数结束——生成器还活着
4. Response 内部 `for chunk in generator` 反复调 `next()`
5. 每 `yield` 一次 → Response 发送一次 → 生成器暂停
6. 函数到底 → `StopIteration` → 连接关闭

### `stream_with_context`

```python
return Response(stream_with_context(generate()), ...)
```

生成器在 `chat()` 函数 return 后还活着——此时请求上下文已被销毁。没有这层包装 → 生成器里访问 `request` 或 `db.session` 可能报 `RuntimeError`。

## 七、CORS 安全加固

```python
CORS(app, origins=[
    "http://localhost:5173",
    # "https://域名.com",  # TODO: 部署后替换
```

`CORS(app)` 不加参数 = 允许所有域名跨域请求。指定 `origins` → 只有列表里的域名能跨域。

## 八、常见 bug

| bug | 表现 | 原因 |
|------|------|------|
| `conv.id` 用于已有会话 | NameError——`conv` 只在 `if None` 分支里创建 | 已有会话时 `conversation_id` 不是 None，过了那个 if，`conv` 不存在 |
| 消息不加 `conversation_id` | curl 返回 200，但 `/api/conversations/<id>` 返回空 | 返回 200 但数据不对——副作用路径没验证 |
| `error_out=False` 忘写 | 手动改 URL 到 `?page=999` → 404 崩溃 | paginate 默认抛异常 |
