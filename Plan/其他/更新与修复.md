# 企业级升级评估：AIChat v1.0

## 项目阶段背景

这是一个零前端经验的开发者正在构建的首个全栈应用，属于学习项目。后端功能已完整（已通过 curl 验证），前端是可用的 MVP。目标是为团队协作和架构思维打下基础。下面列出的问题并非都必须立刻解决——每项都附有“现阶段是否值得做”的判断。

------

## 1. 后端

### 1.1 数据库：没有迁移系统

**问题**：`app.py` 第 25 行在每次启动时调用 `db.create_all()`。这是玩具应用的模式。一旦项目有了真实用户数据，就无法在不丢失数据的情况下修改 schema。企业级应用会使用迁移工具（Alembic）生成带版本号的 SQL 脚本，使 schema 变更可追踪、可回滚、可无损部署。

**替代方案的好处**：Alembic 提供 `alembic upgrade head` 来确定性地应用所有待处理的 schema 变更，`alembic downgrade -1` 可回滚，并且 git 仓库中会记录每一次添加列/索引的历史。在团队中，并行编写迁移的两个开发者不会意外破坏对方的表。

**现阶段是否值得做？** **低优先级**。等项目从 SQLite 迁移到 PostgreSQL 时（即部署时）再添加 Alembic。本地开发时 `create_all()` 快速且够用。现在可以把 `pip install alembic` 加入 `requirements.txt`，但不急于配置。

### 1.2 数据库：User 和 ChatHistory 之间缺乏 ORM 关系

**问题**：`models.py` 中 `ChatHistory` 有外键 `user_id`（第 19 行），但两个模型上都没有定义 `db.relationship(...)`。这意味着无法写出 `user.chat_histories`，只能总是手动编写带 `user_id` 过滤条件的查询。

**替代方案的好处**：在 User 模型上添加 `db.relationship("ChatHistory", backref="user", lazy="dynamic")`，就能获得导航式访问（如 `user.chat_histories.filter(...)`），并且 SQLAlchemy 会自动处理级联删除，而不需要像 `auth.py` 第 66 行那样手动执行 `ChatHistory.query.filter_by(...).delete()`。

**现阶段是否值得做？** **值得，工作量小**。在 User 上添加关系，设置 `cascade="all, delete-orphan"`，然后移除 `delete_account()` 中的手动删除。只需改动 5 行，就能学到 ORM 如何建立图遍历模型。

### 1.3 OpenAI 客户端每个请求都重新实例化

**问题**：`chat.py` 第 36 行在每次 `/api/chat` 调用内部新建一个 `OpenAI(...)` 对象。这会为每个请求分配新的 HTTP 连接池。

**替代方案的好处**：OpenAI 客户端是线程安全的，设计为模块级单例。在导入时（或在 `create_app()` 中）创建一次，就能在所有请求间复用底层的 httpx 连接池，从而降低负载下的延迟，减少内存抖动。

**现阶段是否值得做？** **低工作量，教育价值高**。将 `client = OpenAI(...)` 移到模块顶层（import 之后）。这能学到“昂贵创建、安全共享”对象的模式。现在就做。

### 1.4 SSE 生成器手动重新进入应用上下文

**问题**：`chat.py` 第 43 和 64 行在生成器内部手动捕获 Flask app 对象并调用 `with app.app_context():`。这种做法比较脆弱——虽然因为 Flask 允许 `_get_current_object()` 而能工作，但不符合惯用法。Flask 内置的 `stream_with_context()` 正是为此设计的。

**替代方案的好处**：`flask.stream_with_context(generate())` 包装生成器后，所有 Flask 上下文代理（`current_app`、`g`、`request`）在生成器内都能正常工作，无需手动捕获。代码更少，上下文生命周期出错的概率更低，对任何维护 Flask 代码的开发者都更可读。

**现阶段是否值得做？** **中等**。现有代码可以工作，手动上下文模式也是个很好的学习体验（开发者已经理解了为什么需要它）。但 `stream_with_context` 是标准做法，替换只需改 2 行。为了正确性，现在就做。

### 1.5 SSE 生成器中吞掉了异常

**问题**：`chat.py` 第 58 行是 `except Exception:`，却没有记录实际的异常。如果 DeepSeek API 返回格式错误的 chunk，你只会看到流中出现 `[ERROR]`，没有任何诊断信息。

**替代方案的好处**：至少在 `except` 块中添加 `logger.exception("SSE chunk parse failed")`。在生产系统中，还应分类错误：APIError（限流）、APIConnectionError（网络）和意外的解析失败，并分别响应。

**现阶段是否值得做？** **值得**，在 `except` 块中加入 `logger.exception(...)`。只需一行，就消除了静默失败路径。

### 1.6 没有限流

**问题**：没有任何机制阻止客户端每秒向 `/api/auth/login` 发送 10,000 次请求以暴力破解密码，或通过狂刷 `/api/chat` 耗尽 DeepSeek API 配额。

**替代方案的好处**：Flask-Limiter 可以在登录端点加上 `@limiter.limit("5 per minute")`，在聊天端点加上 `@limiter.limit("30 per minute")`。计数可存放在内存（生产环境用 Redis）。没有它，应用极易被 DoS 攻击和暴力破解。

**现阶段是否值得做？** 现在就把 `flask-limiter` 加入 `requirements.txt`。在公开部署前，为认证端点实现限流。聊天端点等 API 费用成为顾虑时再处理。

### 1.7 没有密码强度校验

**问题**：`auth.py` 接受任意非空字符串作为密码。没有最小长度检查，没有复杂度要求。

**替代方案的好处**：至少 8 个字符（或用 zxcvbn 评估熵值）可以阻止最常见的攻击向量，也避免用户支持问题（比如“我的密码设为‘a’，然后账号被盗了”）。

**现阶段是否值得做？** 在注册和修改密码端点添加最少 6 个字符的检查。改动极小，安全提升立竿见影。

### 1.8 `change_password` 缺少空值校验

**问题**：`auth.py` 第 79–80 行提取 `new_password` 和 `old_password`，但只检查旧密码是否与哈希匹配，从没检查 `new_password` 是否非空就进行哈希。空字符串可以被 werkzeug 正常哈希，所以用户可能不小心把密码设为空。

**现阶段是否值得做？** **值得**。在第 84 行之前添加 `if not new_password: return jsonify({"error": "新密码不能为空"}), 400`。一行即可。

### 1.9 `delete_account`：硬删除，没有确认

**问题**：发送 `DELETE /api/auth/delete-account` 会立即且不可逆地删除用户及其所有聊天记录。没有确认令牌、没有软删除、没有 30 天宽限期。

**替代方案的好处**：企业系统要么要求确认步骤（再次输入密码），要么实现软删除（`is_deleted=True`，查询时过滤）并配合定时硬删除任务。这能防止误触并允许恢复。

**现阶段是否值得做？** **低优先级**（学习项目）。加个注释说明该问题。实现软删除是学习 SQLAlchemy 查询过滤模式的好练习，等项目长大再做。

### 1.10 配置：`DEEPSEEK_API_KEY` 默认值为空字符串

**问题**：`config.py` 第 10 行：`DEEPSEEK_API_KEY = os.getenv("DEEPSEEK_API_KEY", "")`。如果环境变量缺失，应用仍能启动，但每次聊天请求都会因 DeepSeek API 认证失败而报错。应用应该在启动时就快速失败。

**替代方案的好处**：在启动时抛出 `RuntimeError("DEEPSEEK_API_KEY not set")` 或使用 `os.environ["DEEPSEEK_API_KEY"]`（会抛出 KeyError），可以防止部署一个已经坏掉的应用。快速失败是可靠性的核心原则。

**现阶段是否值得做？** **值得**。把 `os.getenv("DEEPSEEK_API_KEY", "")` 改为 `os.environ["DEEPSEEK_API_KEY"]`。一行改动，让开发者学到“启动时大声报错”比“带病运行、让用户踩雷”更好。

### 1.11 `requirements.txt` 缺少生产依赖

**问题**：`requirements.txt` 中没有 `gunicorn`（生产 WSGI 服务器）、没有 `alembic`（迁移）、没有 `flask-limiter`（限流）。Flask 内置的 `app.run()` 是单线程的，不适用于任何生产部署。

**现阶段是否值得做？** 加入 `gunicorn>=21` 和 `alembic>=1.13`。它们不占任何成本，但能提醒开发者这些工具的存在。

## 2. 前端

### 2.1 没有 API 抽象层（`api/` 目录不存在）

**问题**：`CLAUDE.md`、`README.md` 和项目结构文档都列出了 `src/api/` 作为已有目录，并声称有“Axios 封装”。但它并不存在。每个 Vue 组件都直接调用 `axios.post(...)` 或 `fetch(...)`，裸写 URL 和内联 headers。这是文档和实际前端架构之间最大的差距。

**替代方案的好处**：API 层（如 `src/api/index.js` 导出 `login(username, password)`、`sendMessage(text)`）集中管理 base URL、认证 header 注入、错误标准化和 token 刷新逻辑。当后端 API 变更时，只需更新一个文件，而不必翻遍所有组件。这不是“锦上添花”——它是防止后端变更波及到每个视图的边界。

**现阶段是否值得做？** **值得，高优先级**。创建 `src/api/index.js`，用 axios 实例并通过拦截器自动注入 `Authorization` header。这是一个 20 行的文件，能教会“数据访问层”的概念——每个团队代码库都会使用的模式。

### 2.2 没有状态管理（`store/` 目录不存在）

**问题**：`package.json` 中有 Pinia，但从未被实例化。`main.js` 没有调用 `app.use(createPinia())`。没有 `src/store/` 目录。所有状态都是组件本地的 `ref()` 值。认证 token 在多个地方直接读写 `localStorage`。

**替代方案的好处**：一个 Pinia `useAuthStore` 将拥有 token、用户信息和登录/注销动作。组件调用 `authStore.login(...)` 而不是在 Login、Register 和 Chat 之间重复 `localStorage` + axios + router 模式。这是 Vue 3 的规范模式。没有它，增加功能（token 刷新、用户资料、基于角色的访问）就需要触碰每个检查 `localStorage.getItem('token')` 的文件。

**现阶段是否值得做？** **中等优先级**。目前应用只有 3 个视图，重复逻辑尚可管理。但创建 `useAuthStore` 只是一个 30 行的文件，能直接教会“单一数据源”原则——开发者将在未来每个项目中用到。现在可以作为前端下一项任务来做。

### 2.3 没有可复用组件（`components/` 目录为空）

**问题**：完全没有 `src/components/` 目录，但 `CLAUDE.md` 和 `README.md` 将其列为项目目录。`Login.vue` 和 `Register.vue` 共享完全相同的 CSS（Login 第 64–159 行和 Register 第 73–159 行是逐字重复）以及几乎相同的结构。CSS 类 `.page`、`.card`、`.row`、`.btn`、`.error-msg`、`.footer-link` 被定义了两次。

**替代方案的好处**：抽取一个 `<AuthForm>` 组件（使用 slots 或 props）可以避免这种重复。当表单样式改变时，只需改一处。这是组件化架构的核心动机。

**现阶段是否值得做？** **中等**。开发者正处于需要学习“当两样东西看起来相似时，提取组件”的阶段。等 API 层和 store 就位后再做——这是培养前端架构直觉的第三个逻辑步骤。

### 2.4 HTTP 客户端使用不一致

**问题**：`Login.vue` 和 `Register.vue` 使用 `axios.post(...)`。`Chat.vue` 对历史记录使用 `axios.get(...)`，但对 SSE 端点使用原生 `fetch()` 手动读取流。两种不同的 HTTP 客户端、两种错误处理模式、两种注入 auth header 的方式。

**替代方案的好处**：一个统一的 API 客户端（见 2.1）可以同时处理 REST 和 SSE，通过同一个 axios 实例。对于 SSE 流，仍可使用 `fetch()`，但封装在 API 模块中，让调用者不关心传输细节。

**现阶段是否值得做？** **值得**——这其实是 2.1 的子集。创建 API 层后，不一致问题立即解决。

### 2.5 臃肿的 Chat.vue（357 行，所有职责混在一起）

**问题**：`Chat.vue` 同时处理 SSE 流解析（第 58–84 行）、DOM 滚动（第 21–26 行）、错误处理（第 87–109 行）、读取 auth token（第 43 行）、加载历史记录（第 112–125 行）以及整个 UI 模板——全在一个文件里。团队会拆分为：

- `ChatMessage.vue` —— 渲染单条气泡
- `ChatInput.vue` —— 底部输入栏
- `ChatHeader.vue` —— 顶部导航栏
- `useChat.js` —— 发送消息、加载历史、流解析的组合式函数
- `useScroll.js` —— 自动滚动的组合式函数

**替代方案的好处**：每一块都可以独立测试、理解和修改。新加入的开发者不需要读 357 行代码才能改发送按钮颜色。

**现阶段是否值得做？** **低优先级**。开发者还在建立对“何时值得抽取”的直觉。单体目前能工作。等出现具体的复用场景再提取（例如如果设置页也需要顶部栏，再提取 `<ChatHeader>`）。不要让重构过早发生——让重复的痛点驱动提取。

### 2.6 Chat.vue 中重复的错误处理逻辑

**问题**：`Chat.vue` 第 90–92 行和第 98–100 行在同一个 `catch` 块中两次检查 `error.message === 'HTTP 401'`，行为略有不同。第二次检查总是在第一次已经设置消息后执行。这是逻辑错误——第 101 行的 `else` 只有在错误 **不是** HTTP 401 时才会触发，但内部的第二次 401 检查又覆盖了结果。

**替代方案的好处**：清晰的分支结构：如果是 401，设置消息并安排跳转；否则设置通用错误消息。没有重复检查，没有覆盖值。

**现阶段是否值得做？** **值得，立即修复**。这是正确性错误，不是风格问题。第 98 行的第二次 401 检查因为第 90 行已经处理了该情况，属于不可达死代码。

### 2.7 没有 TypeScript

**问题**：所有前端代码都是纯 JavaScript。没有 `tsconfig.json`，没有类型注解。`package.json` 的 devDependencies 中没有 `typescript`、`vue-tsc` 或任何 `@types/*` 包。

**替代方案的好处**：TypeScript 能在编译时捕获 `null.property` 访问、错误的函数签名和 API 响应结构不匹配，而不是在运行时。在团队中，类型就是活的文档——新开发者读函数签名就能知道它接受什么、返回什么，无需看实现。

**现阶段是否值得做？** **暂时不**。开发者正在同时学习 Vue 3、HTTP、CSS 和路由。再引入类型系统会成倍增加认知负担。等前端基础牢固之后再引入 TypeScript——也许放在下一个项目，或等现有代码库稳定后作为一次有意的迁移。

### 2.8 没有 lint 或格式化工具

**问题**：没有 ESLint 配置，没有 Prettier 配置。`package.json` 的 scripts 中没有 `lint`、`format` 或 `type-check` 命令。Vite 脚手架生成时没有包含这些。

**替代方案的好处**：ESLint 能发现未使用变量、缺少 `await` 的异步调用、Vue 特有反模式。Prettier 消除代码审查中的格式争论。两者对 Vue 3 几乎零配置（配合 `@vue/eslint-config-prettier`）。

**现阶段是否值得做？** **低优先级但高价值**。在一个临时项目上运行 `npm create vue@latest` 看一下正确脚手架的样子，然后把 ESLint/Prettier 配置文件复制过来。10 分钟的工作，能永久消除一类 bug。

### 2.9 PWA 文件存在但没有文档化的 PWA 策略

**问题**：`index.html` 注册了 service worker（`/sw.js`）并链接了 `manifest.json`。这些文件存在于 `public/` 并包含应用图标。这意味着应用可以作为 PWA 安装。但没有文档化的离线行为、缓存或更新通知策略。

**现阶段是否值得做？** **无需操作**。当前的 PWA 配置对于“添加到主屏幕”已经可用。高级缓存策略是部署阶段才需要考虑的事。

### 2.10 路由守卫使用基于路径的 auth 检查，而不是 route meta

**问题**：`router/index.js` 第 34 行检查 `if (to.path === '/chat' && !token)`。这种方式不能扩展——每新增一个受保护路由就需要新增一个 `if` 子句。

**替代方案的好处**：为受保护路由添加 `meta: { requiresAuth: true }`，然后在守卫中检查 `to.meta.requiresAuth`。一个守卫覆盖无限路由。

**现阶段是否值得做？** **值得，改动极小**。教会“元数据驱动路由”的模式，这在每个生产级 Vue 应用中都会用到。

### 2.11 将 token 存在 localStorage —— XSS 风险

**问题**：JWT token 存储在 localStorage，页面上的任何 JavaScript 都能访问。若存在 XSS 漏洞（例如从未经处理的聊天消息渲染引入），token 可能被窃取。

**替代方案的好处**：后端设置的 HttpOnly cookie 使 JavaScript 永远无法读取 token。浏览器会在每次请求时自动发送 cookie，配合 `SameSite=Strict`，彻底消除 token 被 XSS 窃取的攻击向量。

**现阶段是否值得做？** **低优先级**（学习项目）。HttpOnly cookie 需要后端改动（登录时设置 cookie）以及 CORS 重新配置。这是生产加固步骤。先记下这个缺口，部署前再实现。

## 3. 开发者体验

### 3.1 没有 Python 项目元数据

**问题**：没有 `pyproject.toml`。`requirements.txt` 存在，但缺少项目元数据（作者、版本、Python 版本约束、依赖分组如 `[dev]` 用于测试工具）。

**替代方案的好处**：`pyproject.toml` 是现代 Python 项目配置标准。可以声明 `[project]` 元数据、`[project.optional-dependencies]` 区分 dev 与 prod 分组，以及工具配置（pytest、ruff、mypy）都在一个文件中。

**现阶段是否值得做？** **低优先级**。项目使用 pip（非 poetry），`requirements.txt` 够用。等项目超过 5 个文件时再引入 `pyproject.toml`。

### 3.2 没有 CI/CD 流水线

**问题**：没有 GitHub Actions、GitLab CI 或自动化部署。每次测试和部署都是手动的。

**替代方案的好处**：在每次 push 时运行 `pytest` 和 `vite build` 的 CI 流水线能在无人干预的情况下捕捉回归。

**现阶段是否值得做？** **暂时不**。项目目前没有可供 CI 运行的测试。等有了测试再添加 CI。

### 3.3 README.md 中写到了 Tailwind CSS，但并未使用

**问题**：`README.md` 第 17 行在技术栈表格中列出了“Tailwind CSS”。但它不在 `package.json` 依赖中，未被配置，项目中也未曾使用。所有样式都是手写 scoped CSS。

**现阶段是否值得做？** 修改 README 以反映现实。描述与代码不符的文档比没有文档更糟糕。

### 3.4 README 列出了 `api/`、`store/`、`components/` 等不存在的目录

同上——`README.md` 和 `CLAUDE.md` 中的项目结构图描述了尚未存在、尚属愿景的目录。

**现阶段是否值得做？** 要么创建这些目录（哪怕是空的），要么更新文档。文档与现实之间的差距会削弱信任。

## 4. 架构

### 4.1 应用工厂太单薄

**问题**：`app.py` 的 `create_app()` 只做了扩展初始化和蓝图注册。对于当前规模来说没问题。但没有“环境特定配置”的概念——没有 `DevelopmentConfig`、`ProductionConfig`、`TestingConfig` 子类。

**替代方案的好处**：基于类的配置层次结构允许将 `DATABASE_URL` 覆盖为内存 SQLite 用于测试，同时保持相同的 `SECRET_KEY` 和 `JWT_SECRET_KEY`。

**现阶段是否值得做？** **低优先级**。目前只有一个环境。等测试基础设施加入后再添加配置子类。

### 4.2 `auth.py` 和 `chat.py` 是普通模块，不是包

**问题**：两者都是单文件蓝图。在这个规模下工作良好。团队会在逻辑增长后将其组织为包（`auth/__init__.py`、`auth/routes.py`、`auth/services.py`）。

**现阶段是否值得做？** **无需操作**。让文件大小作为提取的触发条件——当 `auth.py` 超过 200 行时再考虑拆分。

### 4.3 没有请求/响应序列化层

**问题**：直接返回手写的 dict（`jsonify({"messages": [...]})`）。没有 Marshmallow、Pydantic，甚至模型上也没有手写 `to_dict()` 方法。响应形状是由路由隐式定义的。

**替代方案的好处**：序列化层（Pydantic 模型或 Marshmallow schema）提供校验、文档（自动生成 OpenAPI）和类型安全。避免“这个端点以前返回 `created_at` 现在不返回了”这种回归。

**现阶段是否值得做？** **暂时不**。API 只有 6 个端点。序列化 schema 在 15–20 个端点时才值得投入。等添加 `/api/users` 或 `/api/conversations` CRUD 时再引入。

## 5. 安全

### 5.1 `.env` 中的 API key 是真实的（虽然已被 gitignore）

**问题**：`backend/.env` 包含真实的 DeepSeek API key（`sk-dc1dafa250ec4274855228f527fc7599`）。`.gitignore` 确实排除了 `.env`，所以未提交。但 `SECRET_KEY` 和 `JWT_SECRET_KEY` 的值也是硬编码的，若该文件被意外包含，就会被泄露。

**现阶段是否值得做？** 作为安全卫生练习，轮换 DeepSeek API key（生成新 key，撤销旧 key）。生成正确的随机 secret：`python -c "import secrets; print(secrets.token_hex(32))"`。同时确保存在 `.env.example` 占位值，让新开发者知道该设置什么。

### 5.2 没有 `.env.example` 文件

**问题**：`README.md` 第 58 行写着 `cp .env.example .env`，但 `backend` 目录下没有 `.env.example` 文件。

**现阶段是否值得做？** **立即创建**。这是标准的新人上手约定。

### 5.3 CORS 全开放

**问题**：`app.py` 第 14 行：`CORS(app)` 没有配置。这允许任何域发起跨域请求。生产环境应该限定为 `CORS(app, origins=["https://your-frontend-domain.com"])`。

**现阶段是否值得做？** 记下这个缺口。部署时再限制源。

### 5.4 JWT 没有刷新令牌机制

**问题**：Token 在 2 小时后过期。过期后用户必须重新用用户名/密码登录。没有 refresh token，没有静默续期。

**替代方案的好处**：企业级认证系统会签发短生命周期 access token（15 分钟）和长生命周期 refresh token（7 天，存储在 HttpOnly cookie）。前端自动刷新，无需用户交互。这既提供了安全性（access token 快速过期），又提供了 UX（无需强制重新登录）。

**现阶段是否值得做？** **暂时不**。这是生产级 UX 功能。2 小时过期对开发来说足够了。

### 5.5 没有请求大小限制

**问题**：恶意客户端可以向 `/api/chat` POST 一个 10 GB 的 JSON 体，耗尽服务器内存。Flask 默认没有请求大小限制。

**替代方案的好处**：在 config 中设置 `app.config["MAX_CONTENT_LENGTH"] = 1 * 1024 * 1024`（1 MB）可防止内存耗尽攻击。

**现阶段是否值得做？** 现在就添加这行配置。一行代码，零副作用。

### 5.6 聊天消息输出时未做清理

**问题**：`Chat.vue` 第 156 行渲染 `{{ msg.content }}` 时没有清理。如果用户消息包含 HTML 标签（例如 `<script>alert(1)</script>`），Vue 的模板语法默认会转义，这实际上是安全的（Vue 3）。但如果以后改用 `v-html` 来渲染 markdown，就会成为 XSS 攻击向量。

**现阶段是否值得做？** **低优先级**——Vue 的 `{{ }}` 插值会自动转义。记下这个风险。如果以后加入 markdown 支持，务必使用像 DOMPurify 这样的清理库。

## 6. 测试

### 6.1 零自动化测试

**问题**：整个项目中连一个测试文件都没有。没有 `tests/` 目录，没有 pytest，没有 vitest，没有 jest。唯一测试相关的只有 `Plan/test/` 中的手动 curl 脚本和知识检查文档——不是自动化测试套件。

**自动化测试的重要性**：每次修改后，都必须有人手动 curl 每个端点、点击每个页面来验证没出问题。这种方式无法扩展到一个开发者以上。自动化测试将预期行为编码，一条命令（`pytest`、`npm test`）就能回答“我搞坏了什么？”。

**至少应该有的内容**：

- 后端：使用 pytest 编写 `tests/test_auth.py`（注册、登录、修改密码、注销账号）和 `tests/test_chat.py`（发送消息、获取历史、拒绝空消息）。使用 `pytest-flask` 提供测试客户端。使用内存 SQLite 隔离测试。
- 前端：使用 vitest 为 Login、Register 和 Chat 视图编写组件测试。模拟 API 层，使测试不调用真实端点。

**现阶段是否值得做？** 后端测试是整张清单中价值最高的项目。开发者已经手动 curl 测试了每个端点——将这些检查编码为 pytest 函数，能教会测试金字塔概念，并为将来所有变更建立安全网。前端测试可以等到 API 层和 store 提取后再做。

**推荐顺序**：

1. `pip install pytest pytest-flask` + 创建 `tests/` 目录
2. 先写 `test_auth.py`（端点最简单且最关键）
3. 再写 `test_chat.py`（SSE 测试需要 `app.test_client()` 配合 `stream_with_context`）
4. 每次提交前运行 `pytest`
