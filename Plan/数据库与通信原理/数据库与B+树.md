# 数据库索引与 B+ 树

> 项目：AIChat v1.0  
> 阶段：理解数据库索引底层原理  
> 内容：B+ 树结构 → 聚簇索引 → 全表扫描 → 查询优化器  

---

## 一、B+ 树是什么

### 解决什么问题

数据库需要支持"根据 id 查用户"和"根据 username 查用户"两种操作。数据写在磁盘上，要让查询快，需要特定的数据结构来组织它。

### 结构

```
根节点：       [50 | 100]
               ↓   ↓    ↓
内部节点：  [20|30]  [70|80]  [120|150]
            ↓ ↓ ↓   ↓ ↓ ↓   ↓  ↓  ↓
叶子层（双向链表）：(1→...→20)↔(21→...→30)↔...↔(190→...→200)
```

- 根节点 + 内部节点只存**路标（键 + 指向子节点的指针）**，不存真实数据
- 所有真实数据存在**叶子层**
- 叶子节点之间是**双向链表**——每个叶子有两个指针指向兄弟叶子
- 整体又扁又胖——一般在 3-4 层，能容纳千万级数据行

### 为什么查找是 O(log n)

每次查找从根到叶逐层二分——当前节点的键把区间切成 N+1 个区域，判断目标值落在哪个区域，沿指针向下递归。每下一层就把搜索范围缩小一个数量级。4 层高、每层 256 个键的 B+ 树能索引 256⁴ ≈ 40 亿行数据。

### 为什么节点大小恰好是磁盘一次 I/O 的容量

每个节点的大小设计为磁盘页大小（通常 4KB-16KB）。每次磁盘 I/O 加载一个节点进内存——CPU 在内存里做二分查找。由于树又扁又胖，查一行只需 3-4 次 I/O。**这是数据库和操作系统之间最核心的协作——数据结构节点大小 = 磁盘页大小，每次 I/O 精确用完，没有浪费。**

### 节点分裂与合并（怎么保持平衡）

**插入**：找到目标叶子 → 插入 → 叶子满了（超过容量上限）→ 一分为二 → 新叶子的第一个键被复制到父节点。如果父节点也满了 → 继续向上分裂 → 直到根节点也分裂 → 树长高一层。

**删除**：找到目标叶子 → 删除 → 叶子太饿了（低于半满）→ 向兄弟借数据。如果兄弟也快饿死 → 两个叶子合并。父节点也跟着调整。

数据**只在叶子层**——分裂时内部节点的键只是路标，不是晋升的数据本体。

## 二、聚簇索引 vs 非聚簇索引

### 一张表，两棵 B+ 树

```python
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)              # 聚簇索引
    username = db.Column(db.String(80), unique=True)          # 非聚簇索引
```

users 表上有两棵 B+ 树，不是两张表：

| | 主键索引（聚簇） | username 索引（非聚簇） |
|------|------|------|
| 叶子存什么 | **整行数据** | **username + 主键 id** |
| 排序方式 | 按 id 递增 | 按 username 字典序 |

### 回表

通过 username 查完整行需要两步：

```
① 在 username 索引上查 "zhangsan" → 叶子返回 id=1
② 拿着 id=1 去主键索引再查一次 → 叶子返回完整行（含 password_hash、created_at）
```

多走的第二步叫**回表**——非聚簇索引叶子只有引用，完整数据只存在聚簇索引的一份原稿里。

### 为什么非聚簇索引不存完整副本

完整数据只维护一次——在主键索引里。非聚簇索引只有最小信息。改密码时只更新主键索引，其他索引不动。INSERT 时需要同步写所有索引——但每个索引的叶子很轻量。

### 为什么需要多棵树

一棵 B+ 树的叶子链表**只能按一种顺序排列**。二分查找的前提是数据已排序。要同时支持按 id 查和按 username 查，必须维护两棵各自按不同键排序的树。**一种排序 = 一棵树**，这是物理存储一维性的硬限制，不是 B+ 树的设计缺陷。

### 各索引什么时候需要被更新

| 操作 | 主键索引 | username 索引 |
|------|---------|-------------|
| INSERT 新用户 | 插入整行叶子 | 插入 `(username → id)` |
| 改密码 | 更新整行 | 不动 |
| 改 username | 更新整行 | 删除旧键 + 插入新键 |
| DELETE 用户 | 删除整行 | 删除 `(username → id)` |

索引列不变动时其他树不受影响。索引列被修改时，以该列为键的树也必须更新。

## 三、全表扫描

### 什么时候索引失效

| 情况 | 原因 |
|------|------|
| 查的列没建索引 | B+ 树不存在，数据库只能从叶子从头读到尾 |
| 索引列上做了运算 `LOWER(username)='zhangsan'` | 索引存的是原始值，不是运算后的值——必须逐行读取、执行函数、再比较 |
| 前缀模糊匹配 `LIKE '%zhang%'` | `%` 开头时二分找不到起点——B+ 树无法定位到第一个匹配 |
| 数据量太小（几十行） | 全表扫描 1 次 I/O，B+ 树走 3 层 = 3 次 I/O——优化器故意选了全表扫描 |

### 为什么要给索引列加函数的替代方案

把 `LOWER(username)` 的查询需求前置到写入时——加一列 `username_lower` 存永远小写的用户名，在这列上建索引。查询时直接用 `WHERE username_lower = 'zhangsan'`——B+ 树直接命中，没有函数运算。

## 四、查询优化器

### 它干什么

每条 SQL 执行前，优化器先**不执行**——先估算所有可能的执行路径的成本，选最低的那条：

| 路径 | 成本来自 |
|------|---------|
| 用索引 A → B+ 树二分 → 3 次 I/O | 表统计信息 |
| 用索引 B → B+ 树二分 → 3 次 I/O → 回表 | 表统计信息 |
| 全表扫描 → 叶子从头读到尾 | 表统计信息 |

### 统计信息里有什么

数据库在后台为每张表维护轻量统计数据——不存行内容，只存数值：

| 统计项 | 干什么用 |
|--------|---------|
| 表总共多少行 | 估算全表扫描成本 |
| 索引有多少个不同值（区分度） | 区分度低（如性别只有 2 种值）→ 索引几乎没用 |
| 索引列的 NULL 比例 | 影响成本估算 |
| 数据分布直方图 | 不均匀时精确估计区间内有多少行 |

### 统计信息过期会怎样

优化器拿着过时数据可能选错路径——在全表扫描能更快完成时选了索引。DBA 在大量数据导入后手动执行 `ANALYZE` 更新统计信息。不是数据库不知道索引更快——是它用来判断的统计信息旧了。

## 五、SQLite 文件锁——开发阶段的教训

### 事件

Flask 运行时，用户双击打开了 `backend/aichat.db` 文件（Windows 关联了 SQLite 查看器）。查看器进程抢到了文件锁 → Flask 的 `db.session.commit()` 失败 → 所有在线连接断开，注册的账号也丢失了。

### 根因

SQLite 不是独立进程——是嵌入在 Python 进程内的 C 库，所有数据存为磁盘上的单体文件 `aichat.db`。SQLite 的文件级锁规定**同时只能一个进程以写模式打开**。两个进程争一个文件 → 后来者拿不到锁 → 写入失败。

和 MySQL/PostgreSQL 不同——那些是独立服务器进程，客户端（包括数据库管理工具）统一连到服务器，服务器自己管理并发和文件。不存在"不小心打开了数据文件"的可能——数据文件根本不在客户端可触及的磁盘上。

### 教训

- **SQLite 数据库文件不能在生产运行时直接双击打开。** 即使只是"用工具打开看一眼"，工具也会占用文件锁。
- **要访问数据用 API**——`curl` 调 `/api/history` 查看聊天记录；`curl` 调 `/api/auth/register` 创建测试用户。或者先停 Flask，再打开 `.db` 文件。
- **部署到 Railway 后自动解决**：生产数据库不在本地磁盘上，你无法直接碰它。
